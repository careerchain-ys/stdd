# 変更が壊しうるものを確かめる

変更が**差分の外で**何を壊しうるかを、マージの前に確かめる。メインのセッションで使う。

- **呼び出し元を並べるのが目的ではない。** それは grep で一瞬で出る。探すのは grep では見えない壊れ方である。
- **それらしい説明には価値がない。** 説明は、正しくても間違っていても同じように説得力がある。説明を書く代わりに、
  変更の安全性が依存している事実を 1〜2 個見つけ、**実際にコードを動かして確かめる**。

## 1. 確信の段階

安全性の根拠になる事実ごとに、手間に見合う所まで下の段に進め、どこで止まったかを書く。

| 段 | 内容 |
| --- | --- |
| 1 | そう述べただけ。単独では根拠にならない |
| 2 | 該当する行を示した（`ファイル:行`、またはライブラリの実装の該当箇所） |
| 3 | 失敗の経路を順にたどり、そこへ届かないことを示した |
| 4 | 実際のコードを呼ぶスクリプトかテストを実行した（間違っていれば失敗する形で） |
| 5 | 動いているアプリで再現した |

多くの場合、段 4 は小さなスクリプト 1 本で済む。アプリと同じライブラリを読み込み、気になっている関数そのものを呼ぶ。

## 2. 手順

### 2.1 変更を読む

差分と、追加・変更・削除したシンボル、そして**振る舞いがどう変わったか**を読む。差分に書かれていない変化
（既定値、呼ばれる順序、例外の型、返す値の形）も含める。PR とコミットの説明は `gh pr view`・`git log` で読む。

### 2.2 Spec 側の影響を確かめる

変更したファイルが紐づく要件・設計・テスト設計の ID を逆引きする（方法論 §6.3）。

```bash
bash .claude/hooks/trace-audit.sh --changed $(git diff --name-only origin/<primary_branch>...HEAD)
```

- どの ID にも紐づかない変更は、追跡不能変更として扱う（`rules/stdd-spec-first.md`）。
- 変更が仕様の振る舞いを変えるなら、ここで止めて Spec → テスト → 実装の順に戻る（方法論 §5.2）。
- 文書どうしの影響（要件の変更がどの設計・テスト設計に及ぶか）は、この skill では追わない。
  `verifying-consistency` と、ID の突合・変更の伝播の仕組みに任せる。

### 2.3 安全性が依存している事実を見つける

危うく見える変更の多くは、ある 1 つの事実のおかげで安全である（例: 「この呼び出しが消すのは期限切れの
キャッシュだけで、ほかには何もしない」）。その事実を見つける。それが成り立てば、危うい場合の大半が一度に片付く。
可能性を長く並べるより、ここに時間を使う。

### 2.4 grep が届かない所を見る

- **ライブラリ**: 呼んでいるライブラリの実装を読む。固定しているバージョンと、手元で当てたパッチを確かめる。
- **実行のタイミング**: 非同期の処理の順序、後片付け（破棄・アンマウント・終了時の処理）、再試行。
- **データの形**: API が返す JSON、DB の列、通信の形式、同じデータを読む別の言語のコード、機能フラグ、数段先の利用者。

調べる範囲が広いとき（データの形を読む箇所がリポジトリ全体に散っている、複数のサービスにまたがる）だけ、
探索を subagent に任せ、結論と `ファイル:行` だけを返させる。判断と確かめる作業はメインのセッションで行う。

### 2.5 リスクを正直に書く

リスクごとに、発生条件（どの入力・状態・権限で起きるか）・頻度・影響（気づけるか・戻せるか・誰かの判断を誤らせるか）・
影響先（ユースケースの ID、画面、API の操作、ファイル）を書く。確信の段階（§1）は根拠の強さ、この 4 項目は
リスクの重さで、両方を並べて書く。

- 確かめて問題が無かったものは、リスクと分けて並べる。
- 実在する `ファイル:行` を示す。検索して何も出なかったことも結果として書く。呼び出し元や API を推測で作らない。

### 2.6 事実を確かめ、テストとして残す

事実を確かめるスクリプトかテストを書き、実行し、出力を貼る。

- **仕様の振る舞いに関わる事実**は、使い捨てにせずテストとして残す。対応するユースケースの ID をテストの名前に付け、
  TEST_PLAN.md の該当する行に足す（Spec → テスト → 実装の順を崩さない）。
- **実装の内側の事実**（ライブラリの挙動など）は、壊れたときに気づけるならテストとして残し、そうでなければ
  スクリプトと出力を報告に貼るだけでよい。
- テストの実行は対象を絞る（`commands.test` に対象を渡す）。全件の実行は QA の工程・pre-push・CI に任せる。

### 2.7 大きな変更

変更が大きい・広いときは、独立したレビュー（別のセッションや別のモデルに同じ問いを投げ、答えを突き合わせる）を
勧める。必須にはしない。

## 3. 返すもの

```markdown
## 何が変わったか
<変わったこと。差分から読み取りにくい変化を含める>

## 安全性の根拠になる事実
- <事実>（段 <1〜5>）: <確かめた方法と結果。確かめられなければ「未証明」と書く>

## Spec への影響
<trace-audit.sh --changed の結果。紐づく ID、追跡不能変更の有無、仕様の振る舞いが変わるか>

## リスク
| 壊れ方 | 箇所 | 発生条件 | 頻度 | 影響 | 影響先 | 確かめ方 |

## 確かめて問題が無かったもの
- <対象>: <理由>

## マージの前に
<最も安く実際の不具合を捕まえるテストか再現手順。書いたスクリプトとテストに残したものを含める>
```

公開の場所（PR の本文・コメント）に貼る前に、秘密の値と個人を特定できる情報を除く。

## やらないこと

- 呼び出し元の一覧だけを返して終えない。
- 確かめていない事実を、確かめたように書かない（段を書く）。
- この skill の中で Spec を書き換えない。仕様の振る舞いが変わると分かったら、Spec の更新から始め直す。
