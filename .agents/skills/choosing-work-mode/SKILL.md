# 作業モードを選ぶ（通常 / 緊急）

**既定は通常モード**（`AGENTS.md`・`rules/stdd-spec-first.md`・`auto-implement` などの工程をそのまま通す）。
**緊急モードはユーザーが選んだときだけ入る。** AI が自分の判断で緊急モードに切り替えることはしない
（「時間が無さそうだから」「小さい変更だから」で宣言しない）。背景と考え方は方法論の章
「作業モードと適用限界」（`packages/core/docs/work-modes-and-limits.md`）にある。

- 宣言・確認・解除は同梱の `scripts/work-mode.sh`（この skill のディレクトリからの相対パス）で行う。
- `work-mode.sh declare` は、**ユーザーが発言で「緊急モード」と書いたことの記録**が無いと宣言しない。
  記録はフック `work-mode-prompt.sh`（UserPromptSubmit）がユーザーの発言からだけ残す。
- **申し出や宣言のファイルを直接作ったり書き換えたりしない。** 置き場は誰でも書けるので、仕組みは
  改ざんを防がない。ユーザーが選んだことの控えとして扱う。
- `.stdd.config.yml` の `emergency_mode.enabled` が `false` なら、緊急モードは使えない。通常モードで進める。

## 1. 選ぶ（着手時に 1 回）

- **そのまま §2 へ進むのは次の 2 つだけ**: 依頼文に「緊急モード」と明示がある ／ `/choosing-work-mode` の
  引数で緊急モードが選ばれている。
- **それ以外**（「急ぎで」など速度の表現だけ、`/choosing-work-mode` を引数なしで起動、「緊急モードとは何か」の質問など）は、
  ユーザーに 1 問だけ聞く（選択肢は「通常モード」「緊急モード」。緊急モードなら理由を 1 行で求める）。
  **答えを待たずに宣言しない。** ユーザーが答えの中で「緊急モード」と書けば、その発言が申し出として記録される。
- 通常モードを選んだら何もしない（宣言は作らない）。

## 2. 緊急モードを宣言する

作業用のブランチ（worktree）を作った**あと**で、そのブランチで宣言する。主ブランチでは宣言できない。
宣言はブランチごとで、別のブランチには効かない。

```bash
bash <skill_dir>/scripts/work-mode.sh --root <作業ツリー> declare --reason "<ユーザーが述べた理由を 1 行で>"
bash <skill_dir>/scripts/work-mode.sh --root <作業ツリー> status
```

- 「ユーザーの申し出の記録がありません」と言われたら、宣言せずにユーザーに作業モードを尋ねる（§1）。
- 「記録が古すぎます」と言われたら（既定 120 分。`emergency_mode.request_ttl_minutes`）、緊急モードで進めるかを
  もう一度ユーザーに確かめる。
- **宣言・解除はオーケストレーター（このセッション）だけが行う。** subagent には宣言させない。

## 3. 緊急モードで必須にしないもの

この表は、オリジナルの STDD に**現在ある工程**に合わせている。レビュー工程を変えたときは、この表を差し替える
（方法論の章からはこの表を参照しているので、ほかの場所は直さなくてよい）。

| 対象 | 通常モード | 緊急モード |
| --- | --- | --- |
| Spec のレビュー（Phase 1a / 1b の reviewer と差し戻しループ） | 承認まで回す | **任意**。回すなら 1 回で打ち切ってよい |
| PLAN ドキュメント（Phase 1.5） | 作る | **任意** |
| Red の確認（テストが失敗することを実装前に確かめる） | 必ず行う | **省いてよい**（テストは書く。§4） |
| テストレビュー・QA・コードレビュー（Phase 2.5 / 3 / 4）と、PR 後の `review-pr-with-agents` | 必須。指摘を直して承認まで回す（修正ループは最大 3 回） | **省いてよい**。回すなら 1 回で打ち切ってよい |
| Figma の更新（Phase 4.5） | 行う | **省いてよい**（後追いに書く） |
| フィードバックの棚卸し（Phase 4.8・`recording-dev-feedback`） | 必須 | **行わない**（工程が普段と違うので、プロセス課題の参考値にならない） |
| 品質ゲート（pre-push のテスト・ビルド・トレーサビリティ監査、CI） | 合格が条件 | **不合格を許容**。pre-push のフックは失敗を警告にとどめ、push を止めない |

## 4. 緊急モードでも守るもの

- **Spec → テスト → 実装の順序**（`rules/stdd-spec-first.md`）。振る舞いが変わるなら先に Spec を直し、
  実装と同じ PR に入れる。Spec を後回しにしない。**テストの無い実装だけを入れない**（Red の確認は省いてよい）。
- **人間レビューゲート**（Phase 1a / 1b の、ユーザーによる Spec の確認）。省くかどうかはユーザーが決める。
  エージェントの判断では省かない。
- **作業用のブランチで作業する。** 主ブランチを直接編集しない。破壊的な操作は事前にユーザーの承認を得る。
- **PR 本文の冒頭に「## 緊急モード」の節を書く**（`create-pr`）。次の 4 点を、マージ後に追いかけられる粒度で書く。
  1. 宣言の理由（`work-mode.sh status` の理由）
  2. 省いた工程（例: コードレビュー、Spec の reviewer、Red の確認）
  3. 不合格のまま残した検査の名前（例: `commands.test` の失敗 2 件、トレーサビリティ監査の抜け漏れ）
  4. 後追いが要るもの（未レビューの範囲、不合格の解消、Figma の更新など）
- **工程テレメトリを投稿する**（`create-pr` §5）。レビューをしたかどうかに関わらず `--exempt emergency` で投稿する。
  緊急モードのブランチでは、`pr-telemetry.sh` がこの区分と PR 本文の節を確かめる。集計では緊急モードの PR を
  レビュー回数の統計から外して数える。
- **ほかのフックは変わらない。** spec-first のフック（`spec-first-check.sh`）は緊急モードでも同じように動く。

## 5. 解除

```bash
bash <skill_dir>/scripts/work-mode.sh --root <作業ツリー> clear
```

宣言はブランチに閉じるので、**新しいブランチは通常モードから始まる**。同じブランチで通常の工程に戻すときだけ `clear` する。
