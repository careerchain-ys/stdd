# レスポンスコード体系

API が返す応答の 1 つ 1 つに、意味の決まったコードを付ける規約。コードを、API 設計・画面設計・テスト設計・ログをつなぐ
突き合わせの鍵にする。`API_DESIGN.md` がコードの発生条件を、`SCREEN_DESIGN.md` が受け取ったときの画面の挙動を、
テスト設計がその両方の担保を持つ。

このガイドの既定のうち、**帯の意味と採番の粒度は STDD の既定として固定する**。機能略号の付け方と共通コードの一覧は、
`.stdd.config.yml` の `response_codes` で上書きできる（§5）。

## 1. 応答の形

すべての応答（正常系も含む）にコードを載せる。

| フィールド | 必須 | 内容 |
| --- | --- | --- |
| `code` | ✅ | レスポンスコード。設計書・テスト・ログはこの値で突き合わせる |
| `commonCode` | – | 共通コード（§4）の分類名。共通コードの枠のコードにだけ載せる |
| `data` | – | 正常系のペイロード |
| `message` | – | 開発者向けの補足。利用者に見せる文言ではない |
| `details` | – | 画面が文言に差し込むための構造化データ（違反した項目のパスなど）。構造は `API_DESIGN.md` の応答仕様に書く |

- 利用者に見せる文言は、画面が `code` から選ぶ（文言の正本は `SCREEN_DESIGN.md` の文言・状態カタログ）。`message` を画面に出さない。
- 画面は `commonCode` を見て、知らないコードを受け取っても共通の既定の挙動に戻れる。
- 応答の形（スキーマ・HTTP ステータス・コードの値域）は common の `API_SPEC.md`（または OpenAPI などの定義ファイル）が正本である。

## 2. 形式

`<機能略号>-<帯 1 桁><連番 3 桁>`。例: `ORD-0001` / `ORD-1001` / `ORD-9001`。

| 種別 | 連番 | 定義する場所 |
| --- | --- | --- |
| 機能固有のコード | `001`〜`799` | その機能の `API_DESIGN.md` |
| 共通コードの枠 | `800`〜`999` | 割り当ては §4。各機能の `API_DESIGN.md` にも行を置く |

- 数字部は 4 桁に固定する。桁数が変わると、短いコードが長いコードの先頭と一致する組（`ORD-180` と `ORD-1800`）ができ、検索で取り違える。
- 共通コードも機能ごとに採番する（`ORD-1800`、`USR-1800`）。コードだけで「どの API の応答か」が分かるようにするためである。分類は `commonCode` が持つ。
- 機能略号は要件 ID の `<feature>` と対応させ、プロジェクトの中で一意にする。既定の書き方は英大文字 3〜4 字（§5 で変えられる）。
- 実装では、コードを文字列の定数としてそのまま書く。`"ORD-" + n` のように組み立てると、検索で実装の位置を辿れなくなる。

## 3. 帯と採番の粒度

### 3.1 帯（先頭の 1 桁）

| 帯 | 分類 | 画面から見た性質 |
| --- | --- | --- |
| `0` | 正常系 | 要求が成立した。画面は成功時の挙動（遷移・反映）を行う |
| `1` | 準正常系 | 業務上想定した拒否で、**利用者が入力や選択を直せば回復できる**。画面はフォームの中に理由を示す |
| `9` | 異常系 | 利用者の操作では回復しない（権限・状態の不整合・障害）。画面は汎用のエラー表示か、離脱の導線を出す |

異常系を `2` ではなく `9` に置くのは、同じ表に並ぶ HTTP ステータス（`200` など）と読み違えないためである。

### 3.2 1 分岐 1 コード

**処理が応答を返して終わる分岐 1 つにつき、コードを 1 つ採番する。** `API_DESIGN.md` の処理内容と、機能ルールの判定表で
「ここで応答を返して終わる」箇所を数え、その数だけコードを作る。

- 判定表の拒否の行は、それぞれ別の分岐である。画面での見せ方が同じでも、発生条件が違えば別のコードにする。
- **正常系も、呼び出し元が区別すべき結果の種類ごとに分ける。**

  | 操作 | 分ける結果 |
  | --- | --- |
  | 一覧・検索 | 1 件以上を返した ／ 0 件だった |
  | 冪等な作成 | 新しく作成した ／ 同じキーで作成済みの対象を返した |
  | 更新 | 値が変わった ／ 同じ値で変わらなかった |
  | 冪等な削除 | 削除した ／ もともと存在しなかった |
  | 一括処理 | すべて成功した ／ 一部が成功した（残りは `details`） |

  分けると、テスト設計に「0 件のとき」の行が必ず立つ。1 つのコードにまとめると、0 件なのに通常の成功のコードを返す誤りを検出できない。
- 1 つの分岐に多様な入力から到達する場合は 1 コードにし、内訳は `details` で表す（入力の検証違反は 1 コードで、違反した項目は `details`）。
- 迷ったら分ける。まとめてよいのは、呼び出し元が区別しないと言い切れる場合だけである。後から分けるのはコードの追加で済むが、
  まとめたままにすると、区別すべき結果を画面もテストも見落とす。
- コードは API の中で閉じる。呼び出す画面によってコードを変えない。

### 3.3 一度採番したコードは再利用しない

不要になったコードは非推奨にし、番号を別の意味に使い回さない。過去のログとテストの意味が変わるためである。

## 4. 共通コード

複数の機能で同じ意味と同じ既定の挙動を持つ分類。既定の一覧は次のとおり。

| commonCode | 帯＋連番 | HTTP | 意味 | 既定の画面挙動 |
| --- | --- | --- | --- | --- |
| `VALIDATION_ERROR` | `1800` | 422 | 要求の形式・型・必須・長さの違反 | `details` が指す項目にインラインのエラーを出す。入力を保持する |
| `AUTH_REQUIRED` | `9800` | 401 | 未認証・セッション切れ | ログイン画面へ移る。戻り先を保持する |
| `NOT_FOUND` | `9820` | 404 | 対象が存在しない、または参照できない | 対象が画面の主対象なら「見つからない」状態を表示し、一覧へ戻る導線を出す |
| `INTERNAL_ERROR` | `9900` | 500 | サーバ内部のエラー | 汎用のエラー文言と再試行の導線を出す。入力を保持する |

- 通信の失敗（応答が返らない）は API のコードではないので、画面側で `NETWORK_ERROR` として扱い、`INTERNAL_ERROR` と同じ既定の挙動にする。
- 参照する権限が無い対象は、存在しない対象と同じ応答（`NOT_FOUND`）にする。対象が見えることを許したうえで操作だけを拒むときは、機能固有の `9` 帯のコードにする。
- 画面設計では、共通コードは帯ごとのまとめ行で受けてよい。既定と違う挙動にするときだけ個別の行にして、理由を書く。

## 5. 設定での上書き

```yaml
response_codes:
  feature_code_pattern: "^[A-Z]{3,4}$"   # 機能略号の書き方（正規表現）
  common_codes:                          # 共通コードの一覧。書いた場合は §4 の表を置き換える
    - name: VALIDATION_ERROR
      code: "1800"
      http: 422
      meaning: "要求の形式・型・必須・長さの違反"
      default_behavior: "details が指す項目にインラインのエラーを出す"
```

- `common_codes` の `code` は帯＋連番の 4 桁で、連番は `800`〜`999` にする。帯は §3.1 の意味に合わせる。
- 書かない項目は §4 と既定の書き方のまま使う。

## 6. 要件との分担

- `REQUIREMENTS.md` は利用者から見たエラー（どの場面で何が起き、次に何ができるか）を受入基準に書く。コードは書かない。
- `API_DESIGN.md` は、その受入基準をどの分岐・どのコードで実現するかを書く。
- `SCREEN_DESIGN.md` は、コードを受け取ったときの画面の挙動と文言を書く。

`single` の構成（`TECH_DESIGN.md`）でも同じ規約を使える。その場合は、TECH_DESIGN のエラーハンドリング戦略の表でコードごとに挙動を書く。
