# API_TEST_DESIGN.md テンプレート（feature・バックエンド）

**目的**: [`API_DESIGN.md`](./api-design.md) の行（操作とコードの組・状態遷移・機能ルール・その他処理フロー）ごとに、
どのテストレベルで、どのテストで担保するかを 1 行ずつ定義する。`docs.lineup: layered` の構成で使う。

**配置**: `.stdd.config.yml` の `docs.layout.api_test_design`（例: `docs/<feature>/API_TEST_DESIGN.md`）。`API_DESIGN.md` と対で作る。

**統括との分担**: ユースケースと受入基準ごとの担保先・E2E のシナリオ・テスト対象外は [`TEST_DESIGN.md`](./test-design.md) が持つ。

## 記述基準

- **API_DESIGN のすべての行を列挙する。** 操作ごとのコード・遷移（TR）・業務ルール（BR）・その他処理フロー（FL）に、
  それぞれ 1 行以上を置く。テストしない行も削除せず、`❌` にして根拠の列に理由を書く。
- **すべての行に `AT-NN` を振る**（ファイル全体で通し番号。行を削除しても番号を詰めない）。
- **テストコードには、テスト名に行の ID と対象の ID を含める**（例: `[AT-03] [UC-<feature>-01] 在庫が無ければ XXX-1001 を返す`）。
  ID の書き方は `.stdd.config.yml` の `traceability.patterns.test_tag` に合わせる。
- **テスト参照は「ファイルのパス::テスト名」で書く。** 未実装の間は `TODO` と書き、実装で埋める。ほかの行のテストで担保するときは
  「AT-NN で担保」と書き、同じ検証のテストを重ねて作らない。
- **拒否と失敗の行は、起きないことも確かめる**（データ・件数・更新日時が変わらないこと、副作用が起きないこと）。
- **Integration ではコードと HTTP ステータスの両方を確かめる。**
- 冪等性・同時実行制御が「あり」の操作は、再送・競合のコードの行でその挙動を確かめる。

## 記述しない内容（責務分界）

- ユースケース・受入基準の担保先、E2E のシナリオ、テスト対象外 → `TEST_DESIGN.md`
- 画面のロジックの担保 → `SCREEN_TEST_DESIGN.md`
- コードの発生条件・業務ルールの判定 → `API_DESIGN.md`
- テストデータ・前準備などの実装の詳細 → テストコード
