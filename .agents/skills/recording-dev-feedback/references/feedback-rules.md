# 開発フィードバックの規約

開発中に生じた**プロセス上の課題**（指示の不足、繰り返した手戻り、自動検査で防げたはずの欠陥など）を
GitHub issue として扱うための規約。**この文書が判定基準の正本**であり、手順は
[`../SKILL.md`](../SKILL.md)、仕組み全体の考え方は `packages/core/docs/feedback-loop.md` が持つ。

ラベル名・上限・日数などの値は `.stdd.config.yml` の `feedback` で変えられる。以下では既定値で書く
（`dev-feedback` は `feedback.labels.base`、`priority:high` は `feedback.labels.priority_high` のように読み替える）。

---

## 1. 何を起票するか

判断の基準は 1 つ。**「次の作業や別の機能でも、同じことが起きるか」**。起きるなら起票し、起きないなら
下の表の行き先で処理する。

**起票する**（プロセス・規約・skill / agent に効くもの）:

- コーディングやドキュメントの作法がそろっていない（規約に条項がない、条項があいまいで解釈が分かれた）
- skill / agent の指示が足りず、同じ手戻りや同じ指摘を繰り返した
- テンプレートや規約に書く場所がなく、その都度判断している事項
- 人が毎回口頭で補っている前提（チェックリストや自動検査にできるもの）
- レビューを通過したが、スクリプトで機械的に検出できたはずの欠陥
- 開発フローの手順と、実際の進め方が食い違っている箇所

**起票しない**（別の場所で処理するもの）:

| 事象 | 行き先 |
| --- | --- |
| 対象機能の仕様の誤り・不足 | Spec（REQUIREMENTS.md / TECH_DESIGN.md）を直す |
| 実装のバグ・テスト漏れ | 当該 PR の中で直す |
| 未確定事項・判断待ち | Spec の要確認マーカー（`documenting-requirements` が定める書き方） |
| その場で直せる誤字・整形 | その場で直す |
| その作業限りの TODO | セッション内のタスク管理 |

プロセスの課題ではないが当該 PR の外にある作業（別機能のバグなど）は、`dev-feedback` を**付けずに**
通常の作業 issue として立ててよい。ラベルの有無だけが両者を区別する。

## 2. issue の状態（open ＝ 未反映）

`dev-feedback` の open issue は、**すべて「まだ反映されていないもの」**を意味する。状態は別に管理しない。

- **反映したら閉じる。** 反映先（規約・テンプレート・skill・agent・検査スクリプトなど）を直した PR の本文に
  `Closes #<番号>` を書き、マージで自動的に閉じる。
- **一部だけ反映したときは閉じない。** 反映した部分を本文から削り、残りの作業だけが読める状態にする。
- **反映しないと決めたら `not planned` で閉じる。** 閉じる前に理由をコメントで残す。
- **統合するときは `duplicate` で閉じる。** 残す側の番号をコメントに書き、残す側にも「#<番号> を統合」と書く。
- **起票した PR に `Closes` を書かない。** 起票した PR の中では反映されないので、マージで閉じてはいけない。
- **本文は書き換えない。** 事実の誤りが分かったときだけ、原文を残したまま `訂正` をコメントで追記する。

## 3. 優先度

**作業量ではなく、「後回しにしたときの損失が時間とともに増えるか」で決める。** ラベルはちょうど 1 つ付ける。

| 優先度 | いつ着手するか | 判定 |
| --- | --- | --- |
| `priority:high` | 次の作業単位に入る前 | 後から直すコストが大きく跳ね上がるもの。① すでに実害が出ている（壊れた状態が主ブランチにある、値や決定が失われた） ② 前例が固まる前・ほかが参照する前でないと変えられない（最初の実例がほかの機能へ広がる、参照済みの ID を振り直せない） ③ 同じ種類の課題が繰り返し起きている（§6 の再発の数で判定する） |
| `priority:medium` | 機能が増える前に | 損失が機能の数に比例して増えるもの。いつ入れても効果は同じだが、遅いほど直す対象が増える（検査の新設、skill / agent の補強、テンプレートの追随）。人のレビューで気づきにくい欠陥は、実害がなくてもここに入れる |
| 低 | 着手しない | **起票しない。** いつ直しても損失が変わらないもの（記法や置き場所の一度きりの決定、回避策が確立していて実害が時間だけのもの、影響が 1 ファイル・1 機能に閉じるもの） |

- **低は起票しない。** 起票しても損失は減らず、棚卸しの対象が増えるだけである。既に open の issue を低と判定したら、
  `not planned` で閉じる（「未反映だが着手しない open」は「open ＝ 未反映」と両立しない）。
- **起票しなかったものを後で拾い直す仕組みはない。** 再発は既存の issue を入口に数える（§6）ので、
  起票しなかった事象は次に起きても「初回」になる。拾い直す必要がないことが低の定義であり、それが起票しない根拠になる。
  拾い直したいと感じるなら、それは低ではないので判定をやり直して medium にする。
- 優先度は起票時に付け、後から見直してよい（履歴ではなく現在の判断である）。

## 4. 分類

反映先の種類を表す。当てはまるものをすべて付ける（1 つ以上）。

| キー | ラベル（既定） | 典型的な反映先 |
| --- | --- | --- |
| `spec-format` | `category:spec-format` | Spec のテンプレート、ドキュメント規約、ID の付け方 |
| `skill` | `category:skill` | skill の手順・コード例・禁止パターン |
| `agent` | `category:agent` | agent の定義（担当範囲・指示・観点） |
| `automation` | `category:automation` | フック、検査スクリプト、CI |
| `flow` | `category:flow` | 開発フロー（工程の順序、skill / agent の割り当て） |
| `coding-rules` | `category:coding-rules` | コーディング規約、共通の技術設計 |
| `other` | `category:other` | 起票時に反映先が決まらないもの。本文の「反映先候補」に `未定` と書く |

優先度と分類は**ラベルが正本**である。本文には書かない（二重管理になる）。

## 5. 起票の上限

**1 つの作業単位（1 PR）から起票してよいのは 5 件まで**（`feedback.max_issues_per_pr`）。

数える前に次の 2 つを済ませる。

1. **束ねる。** 同じ反映先を指すもの、同じ種類の欠陥は 1 件にまとめる。
2. **既存の issue があれば再発コメントにする**（§6）。再発コメントは起票ではないので数えない。

それでも上限を超えるなら、優先度の高い順に上限まで起票し、残りは起票しない。同じ優先度なら、
その作業で実際に手戻りを起こしたものを先にする。**ただし「レビューで見逃され、後の段階で見つかった欠陥」は
優先度によらず先に採る**（上限に隠れると、レビュー自体が改善されなくなる）。これは枠の中での順序であり、
枠は増えない。

- **上限を置く理由は、律速が反映の側にあること。** 反映の能力を超えて起票しても反映されず、棚卸しと
  重複確認の手間だけが増える。上限がないと未反映の在庫が際限なく増える。
- **起票しなかった件数を記録する。** 何件起票しなかったかが残らないと、上限が厳しすぎるのか緩すぎるのかを
  後から判断できない。件数は工程テレメトリに記録する（[`../SKILL.md`](../SKILL.md) §6）。
- `dev-feedback` を付けない通常の作業 issue は上限の対象外である。

## 6. 再発と優先度の引き上げ

**同じ事象が再発したら、新しい issue を立てない。** 該当する issue に次の形式のコメントを追加する。

```text
再発 — YYYY-MM-DD（<ブランチ> ／ <PR>）: <一言>
```

- **1 行目は行頭から `再発 —` で書き始める。** 機械が行頭で数えるので、前に記号や空白を付けない。
- **閉じている issue の場合:**
  - `completed` で閉じたもの（反映済み）は reopen する。反映が足りなかった証拠なので、履歴を分けない。
  - 見送り（§7）で閉じたもの、つまり最後の reopen より後に `見送り —` のコメントがあるものは reopen する。
  - **人の判断で `not planned` / `duplicate` にしたものは reopen しない**（コメントだけを残す）。
- **再発コメントが 2 本（`feedback.recurrence_to_high`）に達したら、`priority:medium` を `priority:high` に上げる。**
  起票が 1 回目なので、2 本目は同じ事象の 3 回目にあたる。
  - 数えるのはリポジトリのメンバー（`OWNER` / `MEMBER` / `COLLABORATOR`）が書いたコメントだけ。
  - 上げるだけで、下げない。人が付け直した優先度は、次の再発コメントが来るまでそのままにする。

## 7. 見送り（在庫を増やしすぎない）

起票の上限を設けても、すでにある在庫は減らない。**`priority:medium` の open issue のうち、14 日間
（`feedback.stale_days`）動きのないものは、損失が増えていないとみなして `not planned` で閉じる。**

- **対象**は `dev-feedback` かつ `priority:medium` の open issue。`priority:high` は対象外
  （次の作業単位に入る前に着手する約束なので、動きがないことは見送りの理由にならない）。
- **動きのない期間**は、起票・reopen・コメントのうち最も新しいものから数える。
- **次のどれかに当たるものは閉じない。**
  - open の PR から参照されている
  - assignee が付いている（着手中の印。着手したら自分を assignee にし、手放したら外す）
  - リポジトリ内のファイルから `#<番号>` や issue の URL で参照されている
  - 判定に必要な情報（ラベル・コメント・参照元）を取得できない
- **閉じる前にコメントを 1 本残す。** 1 行目は `見送り — YYYY-MM-DD` で始め、2 行目以降に基準と、再発したときの手順を書く。
- **見送りを当てるのは人で、集計のとき（`measuring-dev-process`）に行う。定期実行では自動化しない。**
  見送りと再発時の拾い直しは対で動く必要があり、片方だけが自動で動くと、閉じたまま誰も気づかない issue が生まれる。
  候補の抽出と適用はスクリプトが行い（`dev-feedback.sh audit` / `close-stale`）、いつ当てるかを人が決める。
- **見送った issue を低に付け替えない。** 低は「拾い直す必要がない」ので起票しないもの、見送りは
  「しばらく再発しなかった」ので閉じるもので、再発すれば §6 で拾い直す。

## 8. 起票の書式

- **タイトル**: 一行の要旨。`FB:` のような接頭辞は付けない（区別はラベルで行う）。
- **ラベル**: `dev-feedback` ＋ 優先度 1 つ ＋ 分類 1 つ以上。
- **本文**: 先頭に記録日・発生源・反映先候補の表（`dev-feedback.sh file` が付ける）、続けて
  [`../templates/issue-body.md`](../templates/issue-body.md) の 3 つの見出し（現象・なぜ問題か・提案）。
  - 「現象」は再現できる具体（ファイル、agent 名、実際のやり取り）で書く。感想は起票しない。
  - 「提案」は反映先に何を足す・直すかを、文面の方向まで書く。決めきれないときは選択肢を並べる。
  - リポジトリ内のファイルへのリンクは絶対 URL で書く（issue の本文では相対リンクが解決されない）。
- **issue を規約の本文の置き場にしない。** 長い規約案は要旨だけを書き、確定した文面は反映先に書く。

## 9. 反映して閉じるとき

反映は起票とは**別の作業単位（別の PR）**で行う。

1. 着手する issue を選ぶ（`priority:high` から）。
2. 自分を assignee にする（`gh issue edit <番号> --add-assignee @me`）。
3. 反映先を直す。本文を書くのは反映先の側で、issue には要旨と反映先だけを残す。
4. PR の本文に `Closes #<番号>` を書く。一部だけの反映なら書かず、issue の本文を残りの作業に縮める。
5. 自分が直した反映先に関係する open issue がほかにないか確かめる。
