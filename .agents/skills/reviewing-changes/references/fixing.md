# 指摘の直し方とラウンドの回し方

`SKILL.md` §5 の詳細。

## 1. 論点ごとに直す

- **ファイル単位ではなく論点単位で直す。** 1 つの論点（1 つの原因）に対する修正を 1 コミットにまとめる。
  1 つのファイルに複数の論点の修正が入るときも、コミットは論点ごとに分ける。どの指摘をどのコミットで直したかを
  台帳（`fixed`）で対応づけるためである。
- **直す前に、もう一度現物を見る。** 指摘を受け取ってから時間が経っていれば、別の修正で状況が変わっていることがある。
- **仕様の振る舞いが変わる修正**は、Spec → テスト → 実装の順に戻る（`rules/stdd-spec-first.md`）。Spec を変えたら、
  次のラウンドで Spec の担当が起動する。
- 修正を subagent や別のセッションに任せるときも、論点ごとに依頼し、裏を取った指摘の内容（`ファイル:行`・再現の手順）を渡す。

## 2. ラウンドと 1 コミットの原則

- 1 つのラウンドは 1 つのコミット（`round start` の時点の HEAD）に対して行う。**ラウンドの途中で修正をコミットしない。**
  報告がそろう前にコミットすると、どの担当がどの断面を見たかが分からなくなる。違反は `round end` が警告するが、止めない。
- ラウンドの後のコミットが、修正済みの指摘が指す修正だけであれば、回し直さずに PR を作れる（ゲートの条件 1）。
  主ブランチの取り込み（merge）はこの条件に含めない。rebase で履歴を書き換えたら、もう一度ラウンドを回す。

## 3. 修正の受け入れ検査（助言）

回し直す前に、修正が本当に指摘を塞いだかを確かめる。ゲートの条件にはしない。

1. 指摘の再現の手順を、修正後のコードでもう一度実行し、意図した出力になることを確かめる。
2. 修正で足したテストが、修正を取り除くと失敗することを確かめる（修正の行を一時的に元に戻すか、わざと壊して実行する）。
   変異（わざと壊すこと）を自動で行う仕組みは技術スタックに依存するので、プラグインが提供していればそれを使う。
3. 結果を指摘ごとに次のどれかに仕分け、完了報告に書く。
   - **直す**: 塞げていなかった。もう一度直す
   - **現在も正しいと確認した**: 再現の手順とテストの両方で確かめた
   - **見送る**: 確かめる手段が無い・手間に見合わない（理由を書く）

## 4. 終え方

- 次のどれかになったら、ゲート（`SKILL.md` §6）に進む。
  - 最後のラウンドで、処置が「直す」「起票」の新しい指摘が出なかった
  - 「直す」はすべて局所的な修正で直し、`fixed` で対応づけた。「起票」は issue にした
- ラウンドの数に上限は設けない。同じ論点の指摘が回し直すたびに出るときは、直し方ではなく前提（Spec や設計）を疑い、
  ユーザーに状況を伝えて判断を仰ぐ。
