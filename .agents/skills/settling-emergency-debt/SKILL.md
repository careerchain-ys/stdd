# 緊急モードの負債を解消する

緊急モードのブランチは、分業・レビュー・品質ゲートの合格を必須にしない（[`choosing-work-mode`](../choosing-work-mode/SKILL.md) §3）。
その間に作った差分を、**通常の開発を止めずに** 1 機能ずつ通常の状態へ戻す。背景は方法論の章
「作業モードと適用限界」（`packages/core/docs/work-modes-and-limits.md`）にある。

- 負債の issue は同梱の `scripts/emergency-debt.sh`（この skill のディレクトリからの相対パス）で読み書きする。
  `gh issue close` を直接使わない（解消の対象に含めていない負債を取りこぼさないよう、スクリプトが確かめる）。
- **この作業自体は通常モードで行う。** 緊急モードを宣言しない。
- **実装を正とするのは着手時点の実装**（§0 の 3 で控える SHA）。着手後に主ブランチへ入った変更には合わせない。
- 判断を減らすため、分岐は §4 の表で決め、**迷ったら人の判断に回す**。人に回す項目は 1 件ずつ質問せず、
  一覧にまとめて PR のレビューで受ける。

## 0. 着手前の確認

1. 対象の負債 issue を決める。指定が無ければ一覧から選ぶ（ユーザーに確かめる）。

   ```bash
   bash <skill_dir>/scripts/emergency-debt.sh list
   bash <skill_dir>/scripts/emergency-debt.sh entries <issue>   # 由来 PR と状態（MERGED / OPEN / CLOSED）
   ```

2. 由来 PR のうち **OPEN のものがあれば、それがマージされるまで着手しない**（解消の対象が動いてしまう）。
   CLOSED（マージされずに閉じた）PR は負債ではないので数えない。
3. 主ブランチ（`.stdd.config.yml` の `project.primary_branch`）の最新から作業用のブランチを作る。その時点の SHA を
   **着手 SHA** として控え、**解消の対象にする由来 PR**（MERGED のものすべて）と一緒に PR 本文に書く。
4. その機能に open な PR があれば、作者と調整してから進める（同じ Spec を同時に直さない）。

## 1. 読む

機能の Spec 一式（`REQUIREMENTS.md`・`TECH_DESIGN.md`・`TEST_PLAN.md` と、触れていれば common 階層）、
着手 SHA の実装、由来 PR の本文の「緊急モード」節（省いた工程・不合格のまま残した検査・後追いが要るもの）を読む。

## 2. 事後レビュー

由来 PR の差分は、通常のレビューを通っていない。`code-reviewer` / `test-reviewer` / `qa-engineer` に、
**由来 PR の差分（`gh pr diff <番号>`）と、着手 SHA の実装**を読ませる。観点は `review-pr-with-agents` と同じでよい。

- レビューの結果は §4 の仕分けの入力にする。ここでは直さない。
- 由来 PR に「不合格のまま残した検査」があれば、着手 SHA で実行し直して、今も不合格かを確かめる。
  主ブランチでも不合格のもの（着手前から不合格のもの）は、この負債として数えない。

## 3. 食い違いを洗い出す

[`verifying-consistency`](../verifying-consistency/SKILL.md) を**機能全体**に当てる（差分ではなく、機能の Spec と実装の全体）。
§2 の結果と合わせて、次を一覧にする。

- Spec と着手 SHA の実装が食い違う箇所（Spec に無い振る舞い・Spec にあるのに実装に無い振る舞い）
- Red を確かめていないテスト（由来 PR の「緊急モード」節に Red の確認を省いたとあるもの）
- トレーサビリティの抜け漏れ（`trace-audit.sh` の指摘のうち、この機能の ID に関するもの）

## 4. 仕分ける

一覧の 1 件ずつに次の表を当てる。

| 状況 | 処置 |
| --- | --- |
| 実装が明らかに誤り（不具合・テストが誤りを固定している） | **実装を直す**（通常の不具合修正。Spec は変えない） |
| 実装の振る舞いが妥当で、Spec が追いついていないだけ | **Spec を実装に合わせる**（§5） |
| 認可・入力検証・エラー時や空の状態の扱い・データの保全・監査に関わる振る舞い | **人の判断に回す**。実装に合わせて Spec から消さない |
| どちらが正しいか決められない・ユーザーへの影響が読めない | **人の判断に回す** |

人の判断に回した項目は、この PR では Spec も実装も変えない。PR 本文に「判断を求める項目」の表
（項目・Spec の記述・実装の振る舞い・選択肢）としてまとめる。

## 5. Spec を実装に合わせる

合わせると決めた項目だけを、通常の Spec の更新として直す（要件は `documenting-requirements`、技術設計は
`documenting-tech-specs`。writer / reviewer を使う場合は `auto-implement` の Phase 1a / 1b と同じ）。

- 要件・技術設計の変更履歴に「緊急モードの負債の解消（実装に合わせた）」と、由来 PR の番号を書く。
- 人間レビューゲート（ユーザーによる Spec の確認）は省かない。合わせた項目の一覧を見せて承認を得る。

## 6. テストが形だけでないかを確かめる

Red を確かめずに入ったテストは、**対象の実装を一時的に壊して、テストが失敗すること**を確かめる
（例: 条件を反転する、返り値を固定する）。壊した内容と結果を PR 本文の確認手順に書き、壊した変更は必ず戻す。
失敗しないテストは直す（`implementer`）。

## 7. 通常モードの工程を通して PR にする

`auto-implement` の Phase 2.5（テストレビュー）→ Phase 3（QA）→ Phase 4（コードレビュー）→ Phase 4.8（フィードバックの棚卸し）
→ Phase 5（PR 作成）を、通常モードのとおりに通す。§2 の事後レビューは、これらの代わりにはならない。

- PR 本文には、着手 SHA・解消の対象にした由来 PR・§4 の「判断を求める項目」を書き、`Refs #<負債 issue>` を付ける
  （`Closes` にしない。着手後に新しい負債が積まれることがある）。
- 工程テレメトリは通常どおり投稿する（`--exempt emergency` は使わない）。

## 8. issue を閉じる

**PR がマージされたあとで**、解消した PR と対象にした由来 PR を渡して閉じる。

```bash
bash <skill_dir>/scripts/emergency-debt.sh close <issue> --settled-by <解消した PR> --handled <由来 PR の番号,...>
```

- 対象に含めていない由来 PR（着手後に積まれたもの）が残っていると、スクリプトは閉じずに止まる（exit 2）。
  issue は open のまま残し、次の解消で扱う。
- 「判断を求める項目」が PR のレビューで決まらなかったときは、その表を issue にコメントで残し、issue は閉じない。
  判断が出たら、この skill をもう一度使って反映する。

## やらないこと

- 着手 SHA より後に主ブランチへ入った振る舞いに Spec を合わせない。
- §4 の表で「人の判断に回す」に当たる振る舞いを、実装に合わせて Spec から消さない。
- 主ブランチで着手前から不合格の検査を、この作業で直しに行かない（別の作業にする）。
