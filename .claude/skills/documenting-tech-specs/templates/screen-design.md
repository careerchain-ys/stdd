# SCREEN_DESIGN.md テンプレート（feature・フロントエンド）

**目的**: 画面の実装に必要な仕様（画面項目・バリデーション・イベント・レスポンス処理・文言）を、
実装者がこのファイルだけで画面を組める粒度で定義する。`docs.lineup: layered` の構成で使う。

**配置**: `.stdd.config.yml` の `docs.layout.screen_design`（例: `docs/<feature>/SCREEN_DESIGN.md`）。画面を持たない機能では作らない。
1 つの機能が複数の画面を持つときは、同じファイルの中で画面ごとに `# UI-<feature>-NN` の見出しを分ける。

**API との分担**: 画面が受け取るレスポンスコードの発生条件は [`API_DESIGN.md`](./api-design.md)、形は common の `API_SPEC.md` が正本である。
本書はコードを受け取ったときの画面の挙動だけを書く。デザインの標準（トークン・共通コンポーネント）は common の `DESIGN.md` を参照する。

## 章立ての骨格

| 章 | 内容 | 適用 |
| --- | --- | --- |
| 1. 画面遷移 | この画面から出入りする遷移 | 常に |
| 2. 画面項目定義 | 項目・選択肢・操作ボタン（ID 付き） | 常に |
| 3. UI ロジック | 3.1 バリデーション → 3.2 イベント処理 → 3.3 レスポンス処理 | 常に |
| 4. 文言・状態カタログ | 項目と状態の組み合わせごとの文言 | 常に |

章 2 は画面の構造（何があるか）だけを書き、振る舞いはすべて章 3 に集める。

## 記法ルール

- **すべての表示項目に ID を振る**（項目 `I-NN`、選択肢 `S-NN`、操作ボタン `B-NN`）。表示だけの項目も含む。
- **データの取得元は「操作名 → フィールドのパス」で書く。** テーブルのカラムを直接指さない（API を経ずにデータベースを読む構成では、
  `TABLE_DEFINITION.md` のカラムを書く）。
- **3.1 バリデーションには、画面が送信前に判定するルールだけを書く。** サーバ側だけで判定する制約は書かず、拒否されたときの見え方を
  3.3 の `VALIDATION_ERROR` の行で受ける。評価の契機と画面の反応は 3.2、違反時の文言は 4 に書く。
- **3.2 イベント処理の画面挙動には、応答を待たずに起きる変化だけを書く。** API を呼ぶイベントは「呼び出す操作」を埋め、
  応答を受けた後の挙動は 3.3 にまとめる。手順が複数あるときは箇条書きにする。
- **3.3 レスポンス処理は操作ごとに `#### 操作名` の節を分け、その操作が返しうるすべてのコードを受ける。**
  - 正常系の結果の種類（0 件・作成済み返却・同値更新・一部成功）は、それぞれ個別の行で受ける。
  - 挙動と文言が同じコードは 1 行にまとめてよい。個別の行を持たない共通コードは、帯ごとのまとめ行で受ける。
  - 共通コードの既定（[レスポンスコード体系 §4](../guides/response-codes.md)）と違う挙動にするときだけ個別の行にし、備考に理由を書く。
  - `RS-NN` は 3.3 の全体で通し番号にする（1 行が複数のコードを受けるので、コードとは別の ID が要る）。HTTP の列は置かない。
  - 画面挙動には、テストでそのまま確かめられる観測可能な挙動（遷移・表示・フォーカス・入力の保持）を書く。
- **4 文言・状態カタログは、項目の列に要素（ボタン・入力・一覧・全体など）、状態の列に場面を分けて書く。** 文言の列には表示する文字列だけを書き、
  補足は備考に書く。次のものは 4 に行を持つ（行が無いと実装が文言を決めてしまう）:
  1. 選択肢を表示する項目の、すべての値の表示ラベル
  2. すべてのバリデーションの違反時の文言（上限超過を含む）
  3. 選択入力の初期値と、未選択の見え方
  4. 表の列見出し（置かない場合も「置かない」と書く）
  5. 任意入力の示し方（ラベルに併記 ／ placeholder ／ 何も出さない）
  6. トーストが消えるまでの時間（または消えないこと）
  7. ローディングの表示の規模（スケルトンの行数・スピナーの位置）
  8. 未設定・0 件・取得失敗のときの代替表示
  9. 日時・数値の表示書式
  10. 複数の値を 1 つの要素に並べる形（区切り記号まで）
  11. 値が null や空のときの表示
- **ID を書く欄には ID を書く。** 「上と同じ」のような参照で置き換えない。

## 記載基準チェックリスト

```
□ 冒頭の表（画面 ID・ルート・対応ユースケース・ワイヤーフレーム）が埋まっている
□ すべての表示項目・選択肢・操作ボタンが ID 付きで章 2 にある
□ 権限による表示・活性の違いが章 2 に表れている
□ この画面が呼ぶ操作が、章 2 のデータの取得元か 3.2 の「呼び出す操作」にすべて現れている
□ 3.1 に画面が判定するルールだけがある
□ 3.2 の API を呼ぶイベントに「呼び出す操作」があり、応答後の挙動は 3.3 にまとまっている
□ 3.3 が操作ごとの節に分かれ、各操作が返しうるすべてのコードが個別の行かまとめ行で受けられている
□ 正常系の結果の種類が個別の行で受けられている（0 件の行と 4 の「空（0 件）」が対応している）
□ 4 が 11 の網羅条件を満たしている
□ 履歴・実装状態の記述が無い（SSOT 原則）
□ 末尾に「テンプレート版: X.Y」があり、その版が本テンプレートの更新履歴にある
```

## 記述しない内容（責務分界）

- コードの発生条件・業務ルールの判定 → `API_DESIGN.md`
- スキーマ・値域 → common の `API_SPEC.md`
- デザインの標準・共通コンポーネント → common の `DESIGN.md`
- テストの担保 → `SCREEN_TEST_DESIGN.md`・`TEST_DESIGN.md`
- ユースケース・受入基準 → `REQUIREMENTS.md`
