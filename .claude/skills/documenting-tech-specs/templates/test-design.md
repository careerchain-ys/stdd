# TEST_DESIGN.md テンプレート（feature・統括）

**目的**: REQUIREMENTS のすべてのユースケースと受入基準について、テストの要否・テストレベル・担保先を 1 か所で示す。
「要件がどこで担保されているか」をこのファイルだけで辿れるようにする。`docs.lineup: layered` の構成で使う。

**配置**: `.stdd.config.yml` の `docs.layout.test_design`（例: `docs/<feature>/TEST_DESIGN.md`）。

**層別のテスト設計との分担**: 操作・業務ルールの行ごとの担保は [`API_TEST_DESIGN.md`](./api-test-design.md)、
画面のロジックの行ごとの担保は [`SCREEN_TEST_DESIGN.md`](./screen-test-design.md) が持つ。本書はそれらの行を担保先として参照し、
E2E のテストだけは本書が直接持つ。

## 章立ての骨格

| 章 | 内容 | 適用 |
| --- | --- | --- |
| 1. ユースケース | ユースケースごとのテストレベルと担保先 | 常に |
| 1.1 受入基準の担保先 | 受入基準ごとに、どの行・どのテストで担保するか | 常に |
| 1.2 E2E のシナリオ手順 | ユースケースの振る舞いを、画面の ID で具体化した手順 | E2E を持つユースケースがある場合 |
| 1.3 機能をまたぐルールの担保 | common の要件にある、機能をまたぐルールのうち本機能が担保するもの | 該当する場合 |
| 2. テスト対象外 | 機能全体としてテストしない事項 | 常に |

## 記述基準

- **REQUIREMENTS §2.1 のすべてのユースケースを章 1 に 1 行ずつ、すべての受入基準を 1.1 に 1 行ずつ列挙する。** テストしない行も削除せず、
  根拠の列か担保先に理由を書く。ユースケースは ID で参照し、名前は複製しない（名前の正本は REQUIREMENTS）。
- **Priority は REQUIREMENTS からそのまま引く。** テストレベルの選び方は方法論の §4（P0 は E2E を必須にする など）に従う。
- **受入基準の参照は「ユースケースの ID ＋ 受入基準の番号」で書く**（受入基準の ID を使うプロジェクトは `AC-<feature>-NN-k`）。
  担保先は層別のテスト設計の行の ID で書き、テストを重ねて作らない。どの行にも紐づかない受入基準は、固有のテストで担保するか、設計の漏れとして設計に戻す。
- **E2E のテスト参照は本書が持つ。** Integration と Unit のテスト参照は層別のテスト設計の各行が持ち、本書は参照だけにする。
- **1.2 の手順は、画面の ID（`UI-` `I-` `B-`）で操作と期待結果を書く。** 文言とセレクタは書かない（文言は SCREEN_DESIGN の 4、セレクタはテストコード）。
  「#」の番号は REQUIREMENTS の振る舞いの手順の番号に対応させる。
- **テスト対象外は本書の章 2 にまとめる。** 層別のテスト設計は対象外の章を持たない。

## 記述しない内容（責務分界）

- ユースケース・受入基準の本文 → `REQUIREMENTS.md`
- 操作・業務ルールの行ごとの担保 → `API_TEST_DESIGN.md`
- 画面のロジックの行ごとの担保 → `SCREEN_TEST_DESIGN.md`
- テストデータ・セレクタなどの実装の詳細 → テストコード
