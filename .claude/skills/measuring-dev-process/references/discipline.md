# 集計と提案の規律

[`../SKILL.md`](../SKILL.md) §2（計器を疑う）と §6（既存を確かめる）の詳細。
どの項目も、集計の数字を誤って読んだり、既にある仕組みを提案し直したりした経験から来ている。

## 1. 計器を疑う

数字を解釈する前に、上から順に確かめる。

| # | 確かめること | 起きやすい誤り |
| --- | --- | --- |
| 1 | 登録簿 §5（計器の既知の問題）に当たる値を使っていないか | 既知の欠陥がある期間の値を、改善の効果として読む |
| 2 | テレメトリの無い PR が、特定の群に偏っていないか | ある作成者や経路の PR だけが投稿しておらず、変更の大半が集計の外にある |
| 3 | 比べる 2 群の条件がそろっているか（レビューの方法、作業の種類） | 条件の違う群の差を、施策の効果と読む |
| 4 | 指標の分母がそろっているか | 同じ名前の指標で、分母の違う値どうしを比べる |
| 5 | 外れ値に支配されていないか（中央値と p90 を並べる。外れ値を除いた値も見る） | 少数の大きな PR が合計の大半を占め、平均が実態を表さない |
| 6 | 母集団の組成が窓の間で変わっていないか | 中央値の変化が、施策ではなく PR の種類の比率の変化で起きている |
| 7 | 取得件数の上限に当たっていないか | 一覧の上限で切り詰められた件数を、在庫の数と読む |
| 8 | 「値が無い」を 0 と読んでいないか | 記録の無い工程を「所要 0 分」と読む |
| 9 | 免除・統合の PR を、レビューした PR と混ぜていないか（緊急モードの `emergency` は、レビューをしていても免除として数える。棚卸しもしないので「棚卸しの記録なし」に入る） | 免除の PR が増えたのを「レビュー回数が減った」と読む |

食い違いを見つけたら、**判定を保留して計器を直す側に回す**（スクリプトの修正は通常の開発フローで行う）。
直すまでの間は、登録簿 §5 に「どの値が・いつから・なぜ使えないか」を書く。

## 2. 提案の前に既存を確かめる

提案 1 件ごとに次の 4 段を踏み、報告の表の 3 欄（既存の仕組み ／ 関係する判断 ／ 棄却済みの代案）を埋める。

1. **主ブランチの現物を当たる。** `git fetch origin` のあと `git grep -n <語> origin/<primary_branch>`。
   手元の作業ツリーは古いことがある。
2. **「採らない理由」を読む。** 関係する skill・スクリプトの説明を「棄却」「採らない」「理由」「判断」で検索し、該当する節を読む。
3. **登録簿の §3（判断）と §4（棄却した案）を読む。** 判断と衝突する提案は、判断を見直す論点として出す（黙って出さない）。
4. **開発フィードバックの既存の issue を当たる。** 同じ課題の issue があれば、提案はその issue を参照する。

典型的な誤り:

- 既にある仕組みを新設として提案する（現物を見ていない）。
- 過去に棄却した案を、理由を読まずに再び出す。
- 既にある仕組みが効いていないのに、もう 1 つ同じ目的の仕組みを足す（問うべきは「なぜ効いていないか」）。

## 3. 提案の書き方

- **1 提案 1 論点。** 「A と B を直す」は 2 行に分ける。
- **効果の見込みを数字で書く**（どの指標が、どの向きへ、どれだけ動くはずか）。登録簿に写したとき、次回の判定の基準になる。
- **費用も書く**（作業の規模、工程に増える時間）。改善が別の工程の時間を増やすことがある。
- **規律を足すなら、自動で確かめる手段を一緒に書く。** 自動化しないなら理由を書く。
- **正しい設計を優先する。** 費用を理由に妥協案を推奨にしない。規模が大きければ、やめるのではなく順番に分ける。
