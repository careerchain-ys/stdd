# 開発フィードバックの記録

作業中に生じた**プロセス上の課題**を GitHub issue として起票する。

- **判定基準の正本は [`references/feedback-rules.md`](references/feedback-rules.md)**。この skill は手順だけを持ち、
  基準を繰り返さない（何を起票するか・優先度・分類・上限・再発の扱いは規約を読んで当てる）。
- 操作は同梱の `scripts/dev-feedback.sh`（以下 `dev-feedback.sh`。この skill のディレクトリからの相対パス）で行う。
  ラベル・上限・再発コメントの書式・昇格の判定はスクリプトが確かめるので、`gh issue create` を直接使わない。
- この skill の範囲は**起票まで**。反映は別の作業単位で行い、反映した PR が `Closes #<番号>` で閉じる（規約 §9）。

`.stdd.config.yml` の `feedback.enabled` が `false` なら、この skill は何もせずに終える。

## 0. 前提を確かめる

```bash
bash <skill_dir>/scripts/dev-feedback.sh check
```

- ラベルが無いと言われたら `dev-feedback.sh setup` を実行する（冪等。導入直後の初回はここで作られる）。
- `gh` が無い・認証されていない場合は、起票をやめて理由をユーザーに伝える。PR の作成は止めない。

## 1. いつ行うか

**レビューを終えたあと、PR を作る前に 1 回だけ行う。** 緊急モードのブランチ（`choosing-work-mode`）では行わない
（工程が普段と違うので、プロセス課題の参考値にならない）。

- 作業の途中で気づいた課題は**その場で起票せず、控えとして手元に持ち越す**。気づいた時点では、
  その PR の中で直せるものかが決まっていない。先に起票して後から PR 内で直すと「open ＝ 未反映」が崩れ、
  棚卸しで同じものを拾って二重起票にもなる。
- ユーザーが起票そのものを指示したときは、その時点で起票する。
- **起票するのはメインのセッション（このセッション）**。reviewer などの subagent には
  起票させない（気づきは完了報告に書かせ、ここで拾う）。

## 2. 棚卸し

作業全体（Spec の作成、実装、レビュー）を振り返り、次の 4 つを拾う。会話が長い場合は git の履歴からも補う。

1. **ユーザーからの訂正** — 「そうではない」「毎回言っている」と指摘された作法や進め方
2. **繰り返した手戻り** — 同じ指摘で 2 回以上やり直した観点、同じ原因で何度も直したエラー
3. **その場しのぎ** — 規約に書かれていないので独自に判断した事項、口頭で補った前提
4. **検査で拾えたはずのもの** — レビューを通過したが、スクリプトで機械的に検出できた欠陥

```bash
# 補助: このブランチで何をしたか（<primary_branch> は .stdd.config.yml の project.primary_branch）
git log --oneline origin/<primary_branch>...HEAD
git diff origin/<primary_branch>...HEAD --stat
```

拾ったものを規約 §1 で仕分け、**起票の対象だけを残す**。対象機能の Spec の誤りや実装のバグは、
起票せずにその場（当該 PR）で直す。迷ったら起票しない側に倒す。優先度が低に当たるものは起票しない（規約 §3）。

## 3. 束ねて、既存を確かめる

1. **束ねる。** 同じ反映先・同じ種類の欠陥は 1 件にまとめる。
2. **既存の issue を探す。** open だけでなく closed も見る（見送りで閉じたものは再発で拾い直す）。

```bash
# 検索語は変数に入れて渡す（語に ' が含まれると引用符が途中で閉じる）
KW='<事象のキーワード>'
gh issue list --label <feedback.labels.base> --state all --limit 50 --search "\"$KW\"" \
  --json number,title,state,stateReason --jq '.[] | "#\(.number)\t\(.state)\t\(.stateReason)\t\(.title)"'
```

3. **既存があれば再発コメントにする**（起票の件数に数えない）。reopen と優先度の引き上げはスクリプトが規約 §6 どおりに判定する。

```bash
bash <skill_dir>/scripts/dev-feedback.sh recur <番号> --note "<一言>"
```

## 4. 上限を当てて起票する

残ったものに**上限**（規約 §5。`feedback.max_issues_per_pr`、既定 5 件）を当て、優先度の高い順に起票する。
レビューで見逃され後の段階で見つかった欠陥は、優先度によらず先に採る。

本文は [`templates/issue-body.md`](templates/issue-body.md) の 3 つの見出し（現象・なぜ問題か・提案）で一時ファイルに書き、
スクリプトに渡す。記録日・発生源（ブランチ・PR）・反映先候補の表はスクリプトが先頭に付ける。

```bash
bash <skill_dir>/scripts/dev-feedback.sh file \
  --title "<一行の要旨>" \
  --priority high|medium \
  --category <分類のキー>[,<分類のキー>...] \
  --target "<反映先のパス。決まらなければ省略（未定になる）>" \
  --body-file <本文のファイル>
```

- 分類のキーは `spec-format` / `skill` / `agent` / `automation` / `flow` / `coding-rules` / `other`（規約 §4）。
- 上限に達していると exit 2 で止まる。**残りは起票せず、件数だけを数えておく。**
- 本文の「現象」は再現できる具体で、「提案」は反映先に足す文面の方向まで書く。リポジトリ内のファイルは絶対 URL で書く。

プロセスの課題ではないが当該 PR の外にある作業（別機能のバグなど）は、このスクリプトを使わず、
`dev-feedback` を付けない通常の issue として立てる（上限の対象外）。

## 5. 棚卸しの終了を記録する

**0 件でも必ず実行する。** 上限で起票しなかった件数を渡す。

```bash
bash <skill_dir>/scripts/dev-feedback.sh triage --skipped <上限で起票しなかった件数>
```

記録は工程テレメトリ（`create-pr` が投稿する）に入り、棚卸しをしたかどうかと件数が後から集計できる。
コマンドが出力する 1 行を、PR の本文の「備考」に入れる。

## 6. 報告する

完了報告に次を含める。

- 起票した issue の番号・要旨・優先度
- 再発コメントにした既存の issue の番号（reopen・昇格したものはその旨）
- 上限を当てた結果（「上限に達しなかった」／「上限に達し N 件を起票しなかった」）
- 起票せずに当該 PR の中で処理したもの（判断が妥当かをユーザーが確かめられるように）

## やらないこと

- 反映先（規約・テンプレート・skill・agent・検査スクリプト）をこの skill で編集しない。起票と反映を同じ PR に混ぜない。
- issue を閉じない。閉じるのは反映した PR、または見送りを決めた人（`measuring-dev-process`）である。
- 起票した issue の番号を PR の `Closes` に書かない（この PR では反映されない）。
- 優先度・分類を本文に書かない（ラベルが正本）。
