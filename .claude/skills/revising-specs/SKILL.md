# 作成済みの機能の改修

要件・設計書・実装がそろっている機能に変更を入れる。メインのセッションで使う。規律の正本は
`packages/core/docs/spec-revision.md`（導入先には配られないので、要点はこの skill に書く）。

- 新規作成は「指定された文書だけを作る」。改修は **「直すべき文書を漏らさない」** を優先する。
  下の文書は上の文書に忠実に書かれているので、上の 1 文が古いまま残ると、すべての検査が通ったまま古い記述に従った実装になる。
- **直す文書を人に列挙させない。** 依存関係から候補を出し、1 件ずつ直すか決める。
- 順序は新規作成と同じ（Spec → テスト → 実装）。

同梱のスクリプトは `<skill_dir>/scripts/spec-propagation.sh`（`<skill_dir>` はこの skill のディレクトリ）。

## 1. 入力と現状を確かめる

1. **対象の機能**（`feature_path`）と**変更の内容**を確かめる。実装中に見つかった欠陥なら、その欠陥の説明でよい。
2. **対象の機能の文書をすべて読む。** `spec-propagation.sh order` で設定にある文書を出し、対象の機能の要件・設計書・テスト設計・
   関係する common の文書・実装を読む。いまの状態を読まずに改修を始めない。
3. **破壊的な変更なら、着手の前にユーザーの承認を取る。** テーブルの列・型・制約の変更、API の互換を壊す変更、レスポンスコードの
   意味の変更は、影響範囲を添えて確かめる。すでに動いている実装とデータがある。

## 2. 変更がどの文書に属するかを決める

| 入口 | 決めること |
| --- | --- |
| 要件が変わった | 起点は要件。§3 の変更の種類を決める |
| 実装中に欠陥が見つかった | 欠陥がどの文書に属するか（見つかった場所ではなく、その事実を持つべき文書） |

実装中に見つかった欠陥は次のように振り分ける。

- 要件の記述が誤っている → 要件が変わった入口に合流する。
- 要件は正しく、設計書やテスト設計がそれを正しく表していない → その文書を起点にする。要件は変えない。
- 文書はすべて正しく、実装だけが違う → 文書は変えない。欠陥を捕まえるテストを足して Red を確かめ、実装を直す（§6 へ）。

決められないときはユーザーに確かめる。実装に合わせて文書を書き換えない。

## 3. 変更の種類と直す文書を決める

1. **変更の種類を決める。** 種類ごとに動くことが多い文書とレビューの強さの目安は
   [`references/change-kinds.md`](references/change-kinds.md) にある（`docs.lineup` の `single` / `layered` の両方）。
2. **依存関係から候補を出す。**

   ```bash
   bash <skill_dir>/scripts/spec-propagation.sh targets <起点の文書のキー> --feature <feature_path>
   ```

   起点の文書から依存の向きにたどれる文書が、直す順に出る（キーは `docs.layout` のキー。例: `requirements`・`api_design`）。
3. **ID と変更前の語で探す。** 変わる ID（`UC`・`BR`・受入基準・レスポンスコード・行の ID）と、変更前の説明文の語の両方を渡す。
   意味が反対になる変更では、ID が残って説明文が古くなるので、語での検索を省かない。

   ```bash
   bash <skill_dir>/scripts/spec-propagation.sh search <ID> "<変更前の語>" ...
   ```

   ほかの機能の文書も探す（`--feature` を付けない）。テストや実装の中も探すときは `--also <パス>` で足す。
4. **候補を 1 件ずつ「直す / 変わらない」に分ける。** 依存関係は ID の参照しか表さないので、2 の候補に 3 の検索結果と
   変更の種類の目安を重ねて決める。変わらないと決めた文書には根拠を残す（§7 の報告に書く）。
   - ID を引いているはずの文書で検索が 0 件なら、その事実は文書に落ちていない。黙って埋めず、報告に書く。

## 4. レビューの強さを選ぶ

| 段階 | 形 | 当てはまる変更 |
| --- | --- | --- |
| 自動検査だけ | reviewer を起動しない | **意味を変えない追随**に限る（文言・体裁、ID の参照の差し替え、上の変更に合わせた要約の書き換え） |
| まとめて 1 回（既定） | すべての文書を直し終えてから、触った文書の reviewer を 1 回ずつ並列に起動する | 意味が変わる設計書・テスト設計の変更 |
| 文書ごと | 書いた直後にその文書の reviewer を起動し、指摘を直してから下へ進む | 要件の意味が変わる変更と、破壊的な変更 |

- 判断の基準は行数ではなく、意味が変わるかどうか。1 行でも意味が変わるなら、自動検査だけで通さない。
- どの段階にしたかは差分を見て決め、判断と根拠を §7 の報告に書く。書けないなら軽い段階を選ばない。
- reviewer の割り当て・起動の仕方・指摘の扱いは `auto-implement` の `references/phases.md`（Phase 1a・1b）と同じ。

## 5. 依存の順に直す

1. **変わった決定を 1 つの文にまとめ、直す文書すべてに同じ文で反映する。** 文書ごとに言い換えない。
   複数の担当（並行するセッションや subagent）に分けるときは、同じ文を同時にすべての担当に渡す。
2. **§3 の順に直す。** 要件は `documenting-requirements`、技術 spec は `documenting-tech-specs` の書き方に従う。
   - 行や ID を削除しても番号を詰めない（欠番にする）。
   - 件数・一覧・しきい値は正本の文書だけに書き、ほかの文書は ID やリンクで参照する。ほかの文書の作成状況や件数を断定しない。
3. **古い記述の残りが無いことを確かめる。** §3 の 3 と同じ語で探し、0 件になることを確かめる。

   ```bash
   bash <skill_dir>/scripts/spec-propagation.sh search --expect-none <ID> "<変更前の語>" ...
   ```

4. **検査を通す。** `trace-audit.sh`（ID の抜け）、`documenting-requirements` の `scripts/state-claims.sh <直した文書>`（転記）。

## 6. テストと実装

文書を直し終えたら、`auto-implement` を `impl-only` で使い、テスト（Red）→ 実装（Green）→ QA → レビュー → PR へ進める。
実装中に新しい欠陥が見つかったら、1 件ずつ止めて差し戻さず、見つかったものをまとめてから §2 に戻る。

## 7. 報告

完了の報告（PR の本文を含む）に次を書く。

- 起点の文書と変更の種類
- 直した文書と、それぞれのレビューの強さ（軽い段階にしたものはその根拠）
- 候補のうち直さなかった文書と、変わらないと判断した根拠
- 検索に使った ID と語、残りの確認の結果（0 件）。ID を引いているはずなのに 0 件だった文書
- 破壊的な変更の有無と、ユーザーの承認
