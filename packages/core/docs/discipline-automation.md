# 規律の自動化

STDD 方法論（[`stdd-methodology.md`](stdd-methodology.md)）の一章。規約や skill に書いた規律を、フック・検査スクリプト・
skill の手順でどう確かめるかを定める。新しい規律を足すときは、この章の手順に従う。

## 1. 目的

STDD の規律の多くは、規約・skill・agent の定義に文章として書かれている。文章の規律は、守るかどうかがエージェントの
判断に委ねられるため、agent の数や工程が増えるほど守られにくくなる。依頼文で明示的に禁じた操作でも、別の agent で
同じ違反が起きることがある。しかも違反の多くは成果物から見分けられない（別の作業ツリーのファイルを編集しても、
同じ名前のファイルがあれば編集は成功する）。

そこで STDD では、規律を文章だけで足さず、それを確かめる自動化と一緒に取り込む。

## 2. 方針

### 2.1 規律は自動化とセットで足す

規約・skill・agent に新しい規律を書くときは、それを自動で確かめる手段を同時に検討する。手段は、効き目の強い順に
次の 4 つから選ぶ。

| 順 | 手段 | 向いているもの |
| --- | --- | --- |
| 1 | ツール実行前のフック（PreToolUse）で、違反する操作をその場で知らせる・止める | 操作の字面で判定できるもの（編集先・実行するコマンド） |
| 2 | 検査スクリプトで違反を検出する（手元・pre-push・CI で実行する） | 成果物の状態で判定できるもの（文書の構造、ID の対応、生成物の一致） |
| 3 | skill の手順に確認のステップとして組み込む | 判断を伴うが、確認する時点は決められるもの |
| 4 | 文章として書くだけにとどめる | 上のどれでも確かめられないもの |

4 を選んだ規律には、自動化しない理由を残す（判断を伴うので機械で判定できない、手間に見合わない、配布の仕組み上
導入先に届けられない、など）。理由は規律と同じ場所か、その仕組みの章の「規律と自動化の対応」の表に書く
（例: [`feedback-loop.md`](feedback-loop.md) §7）。

レビューで見つかった欠陥が同じ型で繰り返し出るときは、レビュー担当への指示を増やすのではなく、検査スクリプトにする。
指示を増やしても、同じ見落としは別のレビュー担当で起きる。

### 2.2 自動化するときに決めること

フックや検査を足すときは、次の 3 点をあわせて決める。

1. **違反時に知らせるか、止めるか。** 強さは `.stdd.config.yml` で切り替えられるようにする（`off` / `warn` / `block`）。
2. **フック自体が失敗したときに通すか、止めるか。** 設定が無い・入力が読めない・必要なコマンドが無いときの扱いを決めて、
   スクリプトの冒頭に書く。STDD のフックは、原則として通す（フックの故障で全作業が止まる害のほうが大きい）。
3. **違反時のメッセージが対処法を示しているか。** 何が違反か、どうすればよいか、例外が要るときはどうするかを、
   メッセージだけで分かるように書く。

### 2.3 止める検査は数を絞り、警告から始める

自動化には代償がある。誤検知で正しい作業が止まると、作業者は例外の手段を常用するか、検査そのものを無効にするように
なる。そこで次のように進める。

- 新しいフックの強さの既定は `warn` にする。誤検知が無いことを確かめてから、プロジェクトの判断で `block` に上げる。
- `block` にする検査は、違反したときの損失が大きく、判定に誤りが出にくいものに絞る。
- 正当な例外がありうる検査には、理由を残して通る手段を用意する（例: 全件テストの `STDD_FULL_TEST_REASON="<理由>"`）。

### 2.4 フックにできないこと

- フックが返せるのは「文脈への注記」か「許可・拒否」だけで、skill を代わりに実行することはできない。
  フックは作業の直前に規律を思い出させる役目で、規律の正本は規約・skill・agent の定義に置く。
- フックが見えるのはツールに渡された文字列だけである。スクリプトの中から起動された子プロセスや、
  シェルの展開結果までは判定できない。フックが防ぐのはうっかりした違反で、意図的な回避ではない。
- 確認を自動で承認する設定や、フックを読み込まない実行環境では効かない。最後の砦は CI の検査と人のレビューである。

### 2.5 プロダクトのコードの段とハーネスの段

§2.1 の 4 つの手段は、ハーネス（規約・skill・agent・フック）の規律を確かめるためのものである。エージェントが
プロダクトのコードで繰り返す間違いには、別の段を使う。上の段ほど効き目が強く、上で塞げるなら下は要らない。

| 段 | プロダクトのコード | ハーネス（§2.1） |
| --- | --- | --- |
| 起きなくする | 構造（状態の持ち主を 1 つにする、やり方を 1 つにする、手で同期する一覧を正本からの生成に替える） | 正本を 1 か所に置き、生成物は検査で一致を確かめる（`check:adapters` など） |
| 書けなくする・その場で止める | 型、lint | フック |
| 成果物で検出する | CI の検査、振る舞いのテスト | 検査スクリプト（pre-push・CI） |
| 確認の時点を決める | — | skill の確認手順 |
| 文章だけ | 文書・規約 | 文章 |

- 間違いがどちらに当たるかは、**どこで起きたか**で決める。コードの書き方の誤りはプロダクトの段、工程の飛ばしや
  編集範囲の逸脱はハーネスの段で塞ぐ。
- どちらの段でも、新しい検査は**実際に起きた間違いで失敗すること**を確かめてから入れる（§5 の手順 4）。
- 繰り返す間違いを見つけて段を選ぶ手順は `correcting-repeated-mistakes` skill が持つ。

## 3. STDD が用意するフック

| フック | 確かめる規律 | 設定（既定） | 対象 |
| --- | --- | --- | --- |
| `spec-first-check.sh` | 実装の前に Spec とテストを更新する | `workflow.enforce_spec_first`（`warn`） | 実装ファイルの編集 |
| `agent-scope-guard.sh` | reviewer はレビューされる作業ツリーを書き換えない。作業ツリーが分かれていなければシェルは読み取りにだけ使う | `workflow.enforce_agent_scope`（`warn`） | reviewer の subagent の編集とシェル |
| `worktree-lock-guard.sh` | subagent は指定された作業ツリーの中で作業する | `workflow.enforce_worktree_lock`（`warn`） | 作業ツリーを宣言したセッションの subagent の編集とシェル |
| `test-scope-guard.sh` | Red / Green の確認ではテストの対象を絞る。全件は QA の工程・pre-push・CI が受け持つ | `workflow.enforce_test_scope`（`warn`） | 対象を絞らない `commands.test` の実行 |
| `pre-push-check.sh` | push の前にテスト・ビルド・トレーサビリティ監査を通す | `traceability.enforce` ほか | `git push` |
| `review-gate.sh` | PR はレビューを通してから作る（[`review-process.md`](review-process.md) §7 の 3 条件） | `workflow.enforce_review_gate`（`warn`） | `gh pr create` |
| `work-mode-prompt.sh` | 緊急モードはユーザーが明示したときだけ入る | `emergency_mode` | ユーザーの発言 |

各フックの判定の詳細と限界は、スクリプトの冒頭のコメントが正本である。登録は Claude が `.claude/settings.json`、
Codex が `.codex/hooks.json`（`scripts/build-adapters.mjs` が生成）で、`pre-push-check.sh` は Claude だけに登録する。

### 3.1 reviewer の書き込みの制限（`agent-scope-guard.sh`）

対象は `requirements-reviewer` / `tech-specs-reviewer` / `test-reviewer` / `code-reviewer` の subagent だけで、
メインのエージェントと QA の agent は対象にしない。設計書と実装はメインのセッションが skill を使って書くので
（[`skill-and-agent.md`](skill-and-agent.md)）、書く側の範囲は、このフックでは確かめない。

守りたいのは「reviewer がレビューされる作業ツリーを書き換えない」ことで、「何も実行しない」ことではない。実行を禁じると
指摘が推測だけになる。そこで、書き込みを一律に防ぐのではなく、作業ツリーを分けたうえで、元の作業ツリーへの書き込みを検出する。

- **分離されているとき**（subagent の cwd の git toplevel が、`CLAUDE_PROJECT_DIR` の toplevel と違う。`isolation: worktree` で起動した
  `test-reviewer`・`code-reviewer`）: シェルは通す。書き込みは、書き込み先の git toplevel がレビューされる作業ツリーと同じときだけ違反とする。
  Claude の作業ツリーはレビューされる作業ツリーのパスの中（`.claude/worktrees/`）にできるので、パスの前方一致では判定しない。
- **分離されていないとき、または `CLAUDE_PROJECT_DIR` が無いとき**（Codex、作業ツリーを分けずに動く agent teams のメンバーなど）:
  書き込みは宛先を問わず違反とし、シェルは読み取りの許可一覧に完全に一致する 1 コマンドだけを許す。連結・パイプ・リダイレクト・置換を
  含むものは違反とする。先頭のコマンド名だけで許可すると、連結や書き込み用のオプションで規律を抜けられるためである。
- **フックで防げないもの**: 分離されたシェルから絶対パスで元の作業ツリーを書き換えること。統合のときにメインのセッションが、
  起動の前後で `git status --porcelain` と HEAD が変わっていないことを確かめて検出する（`auto-implement` の phases.md「作業ツリーを分ける」）。

名前を付けて起動した subagent や agent teams のメンバーでは、入力の `agent_type` に付けた名前が入ることがある。
そのため、agent の名前に「-」と続けた名前（`code-reviewer-security` など）も reviewer として扱う。reviewer に名前を付けるときは
agent の名前で始める。

### 3.2 作業場所の突合（`worktree-lock-guard.sh`）

subagent を起動する側（メインのエージェント）が、作業する作業ツリーを宣言する。宣言は
`auto-implement` skill の `scripts/worktree-lock.sh lock` で行い、git の共通ディレクトリ配下に置かれる（コミットには入らない）。
宣言したセッションの subagent について、書き込み先とシェルの実行先が宣言の内側かを確かめる。宣言していない
セッションには何もしない。

取り違えている当人に作業先を自己申告させても防げないので、宣言は起動する側が行う。相対パスで作業ツリーの外へ出る
コマンド（`../other` など）は判定しない。

### 3.3 全件テストの抑止（`test-scope-guard.sh`）

`commands.test` を、対象（`-` で始まらない引数）を 1 つも渡さずに実行したら知らせる。全件の実行が役割である
`qa-engineer` と、理由を前置した実行は対象にしない。pre-push のフックや CI の中で起動されるテストは、フックを通らないので
影響しない。差分からテストの対象を選ぶ方法は技術スタックに依存するので、STDD 本体では用意しない
（必要ならプラグインで提供する）。

## 4. 規律と自動化の対応

各章で取り込んだ規律と、それを確かめる手段の一覧。新しい規律を足すときは、ここか、その仕組みの章の対応表に行を足す。

| 規律 | 確かめる手段 | 自動化しない部分と理由 |
| --- | --- | --- |
| 実装の前に Spec とテストを更新する | フック `spec-first-check.sh`。ID による影響範囲の確認は `trace-audit.sh` | 変更が仕様の振る舞いを変えるかどうかは判断を伴う |
| 要件・設計・テスト・実装に ID を通す | 検査スクリプト `trace-audit.sh`（pre-push・CI） | — |
| reviewer はレビューされる作業ツリーを書き換えない | フック `agent-scope-guard.sh` と、統合のときの `git status --porcelain`・HEAD の突合 | 分離されたシェルからの絶対パスでの書き込みはフックでは防げず、突合で検出する。agent の名前で始まらない名前を付けて起動した subagent は判定できない（§3.1） |
| reviewer の「直す」に当たりうるテストとコードの指摘には再現を付ける | 統合のときにメインのセッションが再現を実行し直す（`auto-implement` の phases.md） | 再現として十分かは判断を伴う |
| 配る agent に書き込みの道具を持たせない | テスト `test/agent-roles.test.mjs`（[`skill-and-agent.md`](skill-and-agent.md)） | — |
| subagent は指定された作業ツリーで作業する | フック `worktree-lock-guard.sh` と宣言のスクリプト | 宣言するかどうかは起動する側の手順（`auto-implement` Step 4）に任せる |
| Red / Green の確認ではテストの対象を絞る | フック `test-scope-guard.sh` | どのテストが対象かの選び方は技術スタックに依存する |
| skill・agent の正本と生成物は一致している | `npm run check:adapters` | — |
| skill・agent・rule の定義は文字数の上限と総量の基準値を超えない | `npm run check:harness-size`（`docs/config-driven-authoring.md` §7） | 基準値を上げるかどうかは判断を伴うので、理由を PR の本文に書く |
| 着手前に、ほかの作業ツリーや作成中の PR との重なりを確かめる | `work-overlap.sh`（[`parallel-work.md`](parallel-work.md)） | 着手の時点を機械で知る手段が無いので、フックにせず手順で呼ぶ |
| 開発の課題を PR の前に棚卸しする | skill の手順（[`feedback-loop.md`](feedback-loop.md) §7） | 何を起票するかは判断を伴う |
| agent のモデルは別名で書き、判断が中心の agent は既定で下げない | `build-adapters.mjs` の検査（別名以外で失敗）、導入時の設定の検査（`stdd init`）、`test/model-selection.test.mjs`（[`model-selection.md`](model-selection.md)） | どの作業を軽いモデルに任せるかは判断を伴う |
| 緊急モードはユーザーが明示したときだけ入る | フック `work-mode-prompt.sh` と宣言のスクリプト（[`work-modes-and-limits.md`](work-modes-and-limits.md)） | — |
| 変更の安全性が依存する事実を、実行で確かめてからマージする | skill の手順（`assessing-change-impact`）。Spec 側の影響は `trace-audit.sh --changed` | どの事実が根拠になるか、どこまで確かめるかは判断を伴う。確かめたスクリプトは可能ならテストとして残し、以降はテストが確かめる |
| PR はレビューを通してから作る | フック `review-gate.sh` と `review-ledger.sh gate`（[`review-process.md`](review-process.md) §9） | `gh pr create` 以外の方法で作る PR は確かめられない |
| 繰り返す間違いは、指示を足さずに上の段で塞ぐ | skill の手順（`correcting-repeated-mistakes`）。入力は開発フィードバックの再発コメントと工程テレメトリ | どの段で塞げるかは判断を伴う。塞いだ後はその段の検査が確かめる |

## 5. 規律を足すときの手順

1. 規律を一文で書く（何を・いつ守るか）。
2. §2.1 の 4 つの手段から、確かめる方法を選ぶ。文章だけにとどめるなら理由を書く。
3. フックか検査にするなら、§2.2 の 3 点を決め、強さの設定を `.stdd.config.yml` の定義（`packages/core/schema/`）に足す。
   既定は `warn` にする。
4. フックと検査スクリプトにも振る舞いのテストを用意する（`test/` 配下）。繰り返した間違いを塞ぐ検査では、
   実際に起きた間違いを不合格にすべき例としてテストに持たせ、検査がそれで失敗することを確かめる。
5. 規律の正本（規約・skill・agent の定義）に、確かめる手段の名前を書く。§4 の表に行を足す。
