# ID チェーンの突合

STDD 方法論（[`stdd-methodology.md`](stdd-methodology.md)）の一章。要件・設計・テスト設計・テストコード・実装を ID でつなぎ、
どこかで対応が切れていれば検査で見つける仕組みを定める。ID の付け方の基本は方法論の §6、行の ID とレスポンスコード体系は
[`spec-lineup.md`](spec-lineup.md) §4・§5 にある。

## 1. 目的

設計書が増えると、「要件のこの受入基準は、どの設計の行で実現され、どのテストで確かめているか」を人が追い切れなくなる。
特に、API が返すコードと画面がそれを受ける行のように、2 つの文書の間で対応が要るものは、片方を直したときにもう片方が
取り残されやすい。そこで対応を ID の一致として書き、一致しているかどうかを検査で確かめる。

## 2. 2 本のチェーン

| チェーン | つながり |
| --- | --- |
| 要件のチェーン | ユースケース（`UC`）・受入基準・業務ルール（`BR`）→ API 設計・画面設計の行 → テスト設計の行（`AT` / `ST`）→ テストコード → 実装 |
| レスポンスコードのチェーン | API 設計のコード表 → 画面設計のレスポンス処理の行（`RS`）→ テスト設計の行 → 実装中のコードの文字列 |

`single` の構成（`TECH_DESIGN.md` / `TEST_PLAN.md`）では要件のチェーンのうち `UC` と `FL` だけを追う。
`layered` の構成では、加えて設計書の表どうしを突き合わせる。

## 3. 検査の一覧

検査はどちらも `hooks/trace-audit.sh` が行う（pre-push と CI、`verifying-consistency` skill から呼ぶ）。
結果の扱いは `traceability.enforce`（`off` / `warn` / `block`）に従う。

### 3.1 ID の追跡（どちらの構成でも）

| 検査 | 内容 |
| --- | --- |
| 設計漏れ・テスト計画漏れ | 要件のユースケースが、設計書とテスト計画（テスト設計）で参照されている |
| テスト実装漏れ | ユースケースとその他処理フローの ID を持つテストがある（テスト名の ID は `traceability.patterns.test_tag` で見分ける） |
| 実装の注釈 | 実装に `@stdd <ID>` の注釈がある。既定は警告だけで、`require_impl_annotation: true` で抜け漏れにする |
| 孤児参照・ID 重複 | 宣言されていない ID を参照していない。同じ ID を 2 回宣言していない |
| 影響範囲（逆方向） | `--impact <ID>` で ID の全リンク先を、`--changed <file>` で変更したファイルが紐づく ID を出す。レスポンスコードも引ける |

### 3.2 設計書の表の突合（layered）

| 検査 | 内容 |
| --- | --- |
| 文書の組 | 要件にユースケースがある機能は `TEST_DESIGN.md` を持つ。`API_DESIGN.md` と `SCREEN_DESIGN.md` は、それぞれ対になるテスト設計を持つ |
| 表を読めるか | 決まった章と列が見つかる。操作の数とレスポンスコードの表の数が一致する。テスト設計の行が 1 行以上読める |
| コードの形式 | `<機能略号>-<帯><連番 3 桁>` の形で、機能略号が `response_codes.feature_code_pattern` に合う。連番 `800`〜`999` は共通コードの一覧にあり、`commonCode` が一致する。機能固有のコードは `commonCode` を持たない。同じ操作の表に同じコードを 2 回書かない |
| API 設計 → API テスト設計 | 操作とコードの組・状態遷移（`TR`）・機能ルール（`BR`）・その他処理フロー（`FL`）のすべてに、テスト設計の行がある。逆に、テスト設計の行の対象が API 設計にある |
| 要件 → API 設計 | 要件の業務ルールに、API 設計の機能ルールの節がある。機能ルールの節が要件にある |
| API 設計 → 画面設計 | 画面が呼ぶ操作（イベント処理の「呼び出す操作」と、レスポンス処理の操作の節）が返しうるすべてのコードを、レスポンス処理の行が受ける。受け方は、コードを書いた行・帯のまとめ行（`` `9` `` を書いた行）・共通コード名を書いた行のどれでもよい。画面が受けるコードを、その操作が返す |
| 画面設計 → 画面テスト設計 | バリデーション・イベント・レスポンス処理の行のすべてに、テスト設計の行がある。テスト設計の行の対象が画面設計にある。レスポンス処理の行のイベントがイベント処理の表にある |
| 要件 → 統括テスト設計 | 要件のすべてのユースケースが `TEST_DESIGN.md` のユースケースの表にある。すべての受入基準が受入基準の担保先の表に 1 行ずつあり、表に要件に無い受入基準が無い |
| 担保先 | 受入基準の担保先は、テスト設計の行の ID か、テスト参照（`パス::テスト名`）で書かれていて、その行がある |
| テスト参照 | テスト設計に書いたテスト参照のファイルがある |

受入基準は、要件のユースケースの節にある EARS の行（`[WHEN]` などで始まる行）を数える。統括テスト設計では
「ユースケースの ID ＋ 受入基準の番号」か `AC-<feature>-NN-k` で参照する。

## 4. 章名と列名の読み方

- 検査は、章と表を `documenting-tech-specs/references/doc-structure.json` のキーで見分ける。表示名は `project.language` の言語のものを使い、
  `.stdd.config.yml` の `docs.structure` に書いた名前を優先する。スクリプトは章名と列名を持たない。
- 章見出しの番号は見分けに使わない（`## 1. 操作` も `## 操作` も同じ章として読む）。
- `doc-structure.json` を読むのに `jq` を使う。`jq` が無い環境では、表の突合を「未実施」と表示し、合格とは表示しない。
- 1 つの機能の文書は同じディレクトリに置く前提で、ディレクトリを機能の単位として突き合わせる。

## 5. テストの名前の付け方

テストの名前の先頭に、テスト設計の行の ID とユースケースの ID を置く（例: `[AT-03] [UC-orders-01] 在庫が無ければ拒否する`）。
`stdd init` が作る設定の雛形は、この形だけをテストとして数える正規表現を `traceability.patterns.test_tag` に書く。
コメントの中で ID に触れただけの行をテストとして数えないためである。テストフレームワークに合わせて正規表現を変えてよい。

## 6. 検査で見つけられないこと

- **意味の一致**: ID が対応していても、内容が食い違っていれば検査は通る。特に、受入基準をテスト設計に要約して書く段階で取り違えると、
  それより後の文書とテストはすべて整合したまま、誤った実装ができる。要約が要件と一致しているかは、レビュー（`tech-specs-reviewer`）で
  要件の本文と突き合わせて読む。最終的には、実装をわざと壊してテストが失敗することと、結合テストで確かめる。
- **テストが実際に実行されるか**: 検査はテスト参照のファイルがあることまでを確かめる。スキップされたテストや、テストランナーが集めない
  テストを担保として数えないようにするには、テストランナーの収集結果と突き合わせる必要があり、技術スタックに依存するので core には置かない。
- **API の形の定義との一致**: `API_SPEC.md` や OpenAPI の定義とコード表の一致は、定義の形式に依存するので core には置かない。
- **実装から要件への経路の妥当性**: 実装のコードの文字列が要件まで辿れるかは、行の有無までしか確かめない。
- **説明文に残った古い記述**: 仕様を変えたとき、ID の参照が揃っていても、変更前の意味のまま残った説明文は検査では見つからない。
  変更の伝播は [`spec-revision.md`](spec-revision.md) の手順（`revising-specs` skill）で、ID と変更前の語の両方で探して確かめる。

## 7. 規律と自動化

| 規律 | 確かめる手段 | 自動化しない部分と理由 |
| --- | --- | --- |
| 設計書の行には ID を振り、テスト設計は ID で参照する | `trace-audit.sh` の表の突合 | — |
| 操作が返すすべてのコードを、画面とテスト設計が受ける | `trace-audit.sh` の表の突合 | 受け方が妥当か（まとめ行で受けてよいか）は判断を伴うので、レビューで読む |
| 受入基準をテスト設計に転記するときに意味を変えない | レビュー（`tech-specs-reviewer`） | 意味の一致は機械では判定できない（§6） |
