# skill と agent の使い分け

STDD 方法論（[`stdd-methodology.md`](stdd-methodology.md)）の一章。作業を skill（メインのセッションが読み込んで使う手順）に
するか、agent（別の文脈で動く subagent）にするかの基準と、STDD が配る構成を定める。

## 1. 原則

**作業は、既定ではメインのセッションが skill を使って行う。** subagent にするのは、別の文脈で動かすこと自体に意味がある
次の 4 つの場面に限る。

| 場面 | 例 | STDD での使い方 |
| --- | --- | --- |
| 書いた経緯を見ていない目で確かめる | レビュー | reviewer の agent |
| 長い出力をメインの会話の外で読む | 全件のテスト、監査、ログ、広い検索 | `qa-engineer`、検索・要約の subagent |
| 互いに独立した作業を並行に進める | QA とコードレビュー | 同時に起動する |
| 使える道具を制限する | ファイルを書かせない | reviewer の `tools` とフック |

それ以外の作業、特に次のものは subagent にしない。

- **ユーザーとのやりとりに依存する作業**: subagent は会話の履歴を見られない。要件の確定や、ユーザーの指摘を反映する修正は、
  経緯を知っているメインのセッションが行う。
- **順番に進む作業・同じファイルの編集が続く作業**: Spec → テスト → 実装は前の成果物に依存して進む。分けると、
  受け渡しのたびに文脈を集め直すことになり、遅くなるうえに使用量も増える。
- **同じ作業を別の文脈でやり直すだけの委譲**: 同じモデルが同じ作業をしても、結果は良くならない。

subagent はそれぞれ自分の文脈を使い、セッションの使用量の大きな部分を占めうる。起動するのは上の場面に当たるときだけにする。

この原則は、メインのセッションのモデルを問わない。並行にできる部分の扱いは §2 で定める。

## 2. 並行にできる部分

1 つの機能の Spec → テスト → 実装は、単一のセッションで順に進める。一方で、互いに依存しない作業は、並行に進めると
早く終わることがある。並行にするかどうかは、次の条件で決める。

| 作業 | 進め方 | 並行にしてよい条件 |
| --- | --- | --- |
| 1 つの機能の Spec → テスト → 実装 | 単一のセッションで順に進める | —（前の成果物に依存して進むので並行にしない） |
| 同じ成果物の複数の観点のレビュー（QA とコードレビュー、コードレビューの観点ごとの分割など） | 観点ごとに subagent を同時に起動し、メインのセッションが統合する。指摘を確かめ合う必要があれば agent teams | 各レビューが互いの結果を必要とせず、観点が重ならない |
| 互いに独立した機能の開発 | 機能ごとに別のセッションと作業ツリーで進める（[`parallel-work.md`](parallel-work.md)） | 編集するファイルが重ならず、一方の結果を他方が前提にしない |
| 層ごとに担当を分けた開発（画面・API・テストなど） | agent teams か、層ごとのセッション | 層の間の契約（`API_SPEC.md` など）が先に確定しており、編集するファイルが層ごとに分かれている |
| 原因の候補が複数ある調査 | 候補ごとの subagent か agent teams | 候補ごとに独立して確かめられる |

- **agent teams はユーザーが選んだときに使う。** 実験的な機能で既定では無効であり、メンバーの数だけ使用量が増える。
  メンバーどうしで発見を共有し、互いの結論を確かめ合う必要がある作業に向く。結果を返すだけでよい作業は subagent で足りる。
- **レビューは観点を分ける。** 1 体の reviewer は一度に 1 種類の問題に注意が偏りやすい。並行にするときは観点を 1 つずつ渡し、
  重ならないようにする（`auto-implement` の phases.md「観点を分けた並行レビュー」）。
- **同じファイルを複数で編集しない。** 並行に書く作業は、担当するファイルを先に分けてから始める。
- **並行に書く前に、共有する前提を確定させる。** 要件と、層の間の契約は、並行に書き始める前に確定させる。
  並行に書いている途中で前提が変わると、すべての担当に手戻りが広がる。
- **長く自律的に動かすときは、時間の目安を渡す。** 経過時間と目安を伝えると、予定の範囲で終えやすくなる。
  完了の報告は結果の報告として受け取り、テストや差分で確かめてから完了とする。
- **subagent のモデルを確かめる。** 並行に起動するほど、subagent のモデルの選び方が使用量に効く。

## 3. STDD の構成

| 作業 | 形 | 理由 |
| --- | --- | --- |
| 要件・技術設計・PLAN を書く | skill（`documenting-requirements` / `documenting-tech-specs` / `documenting-plans`） | ユーザーとのやりとりに依存し、順番に進む |
| テストと実装を書く | skill（`auto-implement` の `references/implementation.md`） | 同じファイルの編集が続き、Spec とテストに依存する |
| Spec・テスト・コードのレビュー | agent（`requirements-reviewer` / `tech-specs-reviewer` / `test-reviewer` / `code-reviewer`） | 書いた経緯を見ていない目で確かめる。ファイルは書かない |
| QA | agent（`qa-engineer`） | 全件のテスト・監査・動作確認の長い出力を外で読み、要約だけを返す |
| 工程の進行 | skill（`auto-implement`） | メインのセッションが skill を順に使って進める |

- reviewer は、対象の変更があるときだけ起動する（条件は `auto-implement` の `references/phases.md`「reviewer の使い方」）。
- reviewer には、対象のファイルと基準の Spec のパスを渡し、書いたときの判断の理由は渡さない。理由を渡すと、
  書いた側と同じ見方でしか確かめられなくなる。
- 指摘を直すのはメインのセッションである。reviewer はファイルを書かず、指摘を結果として返す。
- STDD の工程は agent teams を前提にしない。順番に進む作業や同じファイルの編集には単一のセッションのほうが向くためである。
  subagent は通常の委譲の仕組み（Codex は `multi_agent`）で起動する。並行にできる部分で使うかどうかは §2 の条件で決める。

## 4. agent と skill を足すとき

- **agent を足すのは、§1 の 4 つの場面のどれかに当たるときだけ**にする。当たらない手順は skill（または既存の skill の
  `references/`）に書く。
- **配る agent には書き込みの道具を持たせない。** 書く作業はメインのセッションが行うので、agent の `tools` に
  `Edit` / `Write` などは入れない（検査は §6）。
- **委譲を促す常設の指示を書かない。** skill・agent・規約に「〜は必ず subagent に任せる」と書くと、要らない場面でも
  委譲が増える。委譲する場面は、§1 の理由とともに、その工程の手順の中にだけ書く。
- **絶対の言い方には範囲と理由を添える。** 「必ず」「禁止」とだけ書いた指示は、想定していない場面にも一律に効く。
  どの場面で・なぜそうするかを書く。例外なく守らせたいものは文章ではなくフックや検査にする
  （[`discipline-automation.md`](discipline-automation.md)）。
- skill の説明（`description` と `when_to_use`）は、すべてのセッションで常に読み込まれる。skill を足すときは、
  既存の skill の `references/` に置けないかを先に検討する（文字数の基準は `docs/config-driven-authoring.md` §7）。

## 5. Codex と既存の導入先

- Codex 向けの生成物も同じ構成である。`.codex/agents/` には reviewer と `qa-engineer` だけを配り、書く作業は
  メインのセッションが skill で行う。
- 既に導入しているプロジェクトでは、`stdd init` を再実行すると、配布から外れた agent の定義は、編集していなければ削除される。
  編集していた定義は残り、その旨が報告される。残った定義は `auto-implement` から呼ばれなくなる。

## 6. 規律と自動化の対応

| 規律 | 確かめる手段 | 自動化しない部分と理由 |
| --- | --- | --- |
| reviewer はファイルを書かず、シェルは読み取りにだけ使う | フック `agent-scope-guard.sh`（`discipline-automation.md` §3.1） | 名前を付けて起動した subagent は判定できない |
| 配る agent に書き込みの道具を持たせない | テスト `node --test test/agent-roles.test.mjs` | — |
| subagent にするのは §1 の場面に限り、並行にするのは §2 の条件に当たるときに限る | 文章のみ（この章と `auto-implement` の手順） | 委譲や並行が妥当かは作業の中身による判断で、機械では決められない |
