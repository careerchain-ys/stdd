# 設計書のラインナップと章立て

STDD 方法論（[`stdd-methodology.md`](stdd-methodology.md)）の一章。feature 階層の技術 spec をどの文書に分けるか（ラインナップ）と、
各文書の章・表・行の ID の決め方を定める。テンプレートは `documenting-tech-specs` skill の `templates/` にある。

## 1. 目的

新しいプロジェクトで STDD を導入するとき、最も手間がかかるのは、プロジェクトに合う設計書の構成と章立てを作ることである。
STDD は、そのまま書き始められる構成を 2 つ用意し、`.stdd.config.yml` の `docs.lineup` で選べるようにする。

## 2. 2 つの構成

| `docs.lineup` | feature の技術 spec | 向いている場面 |
| --- | --- | --- |
| `single`（省略時） | `TECH_DESIGN.md`（技術設計）・`TEST_PLAN.md`（テスト戦略） | 小さなアプリ、画面と API を同じ担当が同時に書く構成 |
| `layered`（新規導入の既定） | `API_DESIGN.md`・`API_TEST_DESIGN.md`（バックエンド）、`SCREEN_DESIGN.md`・`SCREEN_TEST_DESIGN.md`（フロントエンド）、`TEST_DESIGN.md`（機能全体のテストの担保） | 画面と API が分かれ、テストの実行環境とレビューの観点が層ごとに違う構成 |

- `stdd init` が作る設定の雛形は `layered` である。`docs.lineup` を書いていない設定は `single` として扱うので、導入済みのプロジェクトは今の構成のまま動く。
- `layered` で API を持たない機能は API の 2 本を、画面を持たない機能は画面の 2 本を作らない。
- 要件（`REQUIREMENTS.md`）と common 階層（`ARCHITECTURE.md` / `TABLE_DEFINITION.md` / `API_SPEC.md` / `DESIGN.md`）は、どちらの構成でも同じである。
- 計画書（PLAN）はどちらの構成でも任意である（`docs.layout.plan` を書いたときだけ作る）。

## 3. layered の文書の分担

| 文書 | 持つもの | 持たないもの |
| --- | --- | --- |
| `API_DESIGN.md` | 操作ごとの基本情報表（使用 API・種別・対応ユースケース・認可・冪等性・同時実行制御・トランザクション・副作用）、レスポンスコードと発生条件、処理内容（判定の順序）、応答仕様（一覧の並び順・ページング・0 件のとき）、状態遷移、業務ルールの実現方法、その他処理フロー | API の形（パス・スキーマ。common の `API_SPEC.md`）、画面の挙動 |
| `SCREEN_DESIGN.md` | ID 付きの画面項目・選択肢・操作ボタン、UI ロジックの 3 つの表（バリデーション・イベント処理・レスポンス処理）、文言・状態カタログ | コードの発生条件、業務ルールの判定 |
| `API_TEST_DESIGN.md` | API_DESIGN の行（操作ごとのコード・遷移・業務ルール・その他処理フロー）ごとの担保 | ユースケースと受入基準の担保先 |
| `SCREEN_TEST_DESIGN.md` | SCREEN_DESIGN の行（条件を持つ項目・バリデーション・イベント・レスポンス処理）ごとの担保 | 同上 |
| `TEST_DESIGN.md` | ユースケースと受入基準ごとの担保先、E2E のシナリオ手順、機能をまたぐルールの担保、テスト対象外 | 層別の行ごとの担保 |

API と画面を分けると、「API が返すコードを、画面がどう受けるか」を文書の間の参照として書ける。画面設計のレスポンス処理は、
呼ぶ操作が返すすべてのコードを行として受ける。これを機械で突き合わせられるように、コードの体系を決めておく（§5）。

## 4. 行の ID

| 文書 | ID | 意味 |
| --- | --- | --- |
| `REQUIREMENTS.md` | `UC-<feature>-NN` / `BR-<feature>-NN` | ユースケース / 業務ルール |
| `API_DESIGN.md` | `TR-NN` / `FL-<feature>-NN` | 状態遷移の行 / その他処理フロー |
| `SCREEN_DESIGN.md` | `UI-<feature>-NN` / `I-NN` `S-NN` `B-NN` / `VA-NN` `EV-NN` `RS-NN` | 画面 / 項目・選択肢・ボタン / バリデーション・イベント・レスポンス処理の行 |
| `API_TEST_DESIGN.md` / `SCREEN_TEST_DESIGN.md` | `AT-NN` / `ST-NN` | テスト設計の行 |
| 全体 | レスポンスコード（`ORD-1001` など） | 応答の分岐 |

- 設計書が ID を採番し、テスト設計はその ID を参照する。設計書にはテストの情報を書かない。
- 行の ID は文書の中で通し番号にし、行を削除しても番号を詰めない。参照とテストの名前が壊れるためである。
- `UC` と `FL` は `trace-audit.sh` が要件 → 設計 → テスト計画 → テスト → 実装の順に追う。設計書とテスト計画のファイル名は `docs.layout` から読む。

## 5. レスポンスコード体系

API を持つ構成では、応答の分岐ごとにコードを付ける（`documenting-tech-specs/guides/response-codes.md`）。

- **帯**: `0` は正常系、`1` は利用者が入力を直せば回復できる拒否、`9` は利用者の操作では回復しない異常。
- **粒度**: 応答を返して終わる分岐 1 つにつき 1 コード。正常系も、呼び出し元が区別すべき結果の種類ごとに分ける（一覧の 0 件など）。
- **共通コード**: 連番 `800`〜`999` を共通コードの枠として予約し、既定の画面挙動を決めておく。

帯の意味と粒度は STDD の既定として固定する。機能略号の付け方と共通コードの一覧は、プロジェクトによって違うので `response_codes` で上書きできる。

## 6. 章名・列名と言語

- ファイル名は英語に統一する（`API_DESIGN.md` など）。
- 章名・表の列名・表の行の名前・行の ID の接頭辞は、`documenting-tech-specs/references/doc-structure.json` に言語ごと（`ja` / `en`）に定義する。
  キーは言語に依らない識別子で、検査スクリプトはこのキーで章と表を見分ける。
- プロジェクトで名前を変えるときは、`.stdd.config.yml` の `docs.structure` に書く。検査は設定を先に読み、無ければ既定の名前を使う。
- テンプレートの本文は日本語である。

## 7. テンプレートの版

- 各テンプレートは、記法ルール・記載基準のチェックリスト・書かない内容（ほかの文書との分担）・更新履歴を持つ。
- 書いた文書は、末尾に基づいたテンプレートの版（`テンプレート版: X.Y`）を宣言する。テンプレートを変えたら版を上げ、
  更新履歴に作成済みの文書の直し方を書く。どの文書を直せばよいかを、版の宣言から探せるようにするためである。

## 8. 書く人とレビューする人

- 書く作業は、どの文書もメインのセッションが `documenting-tech-specs` skill を使って行う（[`skill-and-agent.md`](skill-and-agent.md) §3）。
  `layered` では、`API_DESIGN.md` → `SCREEN_DESIGN.md` → 層別のテスト設計 → `TEST_DESIGN.md` の順に書く。
- レビューは `tech-specs-reviewer` が行う。文書ごとに reviewer の定義を分けず、設計書と対になるテスト設計の組ごとに並列に起動する
  （API の組・画面の組・`TEST_DESIGN.md` と要件の組）。理由は次の 2 つである。
  - agent を足すのは、別の文脈で動かすこと自体に意味がある場面に限る（`skill-and-agent.md` §4）。観点ごとの並列のレビューは、
    同じ定義に対象と観点を渡す形で足りる（同 §2）。
  - 設計書とテスト設計は、行が 1 対 1 で対応しているかを突き合わせて見る必要がある。組で渡すと、1 回のレビューでそれを確かめられる。

## 9. 規律と自動化の対応

| 規律 | 確かめる手段 | 自動化しない部分と理由 |
| --- | --- | --- |
| テンプレートの章名・列名・版の宣言が構造定義と一致する | テスト `node --test test/doc-structure.test.mjs` | — |
| `layered` の設定は `test_design` と、API か画面の設計書とその対のテスト設計を持つ | 設定の JSON Schema（`docs.lineup` による条件） | — |
| すべてのユースケースが設計書とテスト計画に載り、すべてのフローがテスト計画に載る | `trace-audit.sh`（`docs.layout` のファイル名で設計書とテスト計画を見分ける） | — |
| 設計書の行とテスト設計の行が 1 対 1 で対応する。画面がすべてのコードを受ける | `tech-specs-reviewer` のレビュー | 表どうしを突き合わせる検査はまだ無い。足すときは、章名と列名を構造定義と `docs.structure` から読む形にする |
| 書いた文書の章名・列名がテンプレートのとおりで、末尾に版がある | `tech-specs-reviewer` のレビュー | 書いた文書の構造を確かめる検査はまだ無い。足すときは上と同じ形にする |
