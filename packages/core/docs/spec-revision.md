# 仕様変更への追随

STDD 方法論（[`stdd-methodology.md`](stdd-methodology.md)）の一章。要件・設計書・テスト・実装がそろっている機能に変更を入れるときの
進め方と、変更を文書の間で漏れなく伝える方法、値を文書の間で書き写さない規律を定める。手順は `revising-specs` skill が持つ。

## 1. 目的

新しい機能を作るときは、要件から順にすべての文書を書く。作成済みの機能を変えるときは、変わる文書だけを直せばよい。
その代わりに、**直すべきなのに直さなかった文書**が欠陥になる。下の文書は上の文書に忠実に書かれているので、
上の文書の 1 文が古いまま残ると、下の文書もテストもその古い記述に従ったまま、すべての検査が通ってしまう。

そこで改修では、新規作成と優先することを変える。

| | 新規作成 | 改修 |
| --- | --- | --- |
| 優先すること | 指定された文書だけを作る | 直すべき文書を漏らさない |
| 対象の文書の決め方 | 人が指定する | 文書間の依存関係から決める（人に列挙させない） |
| レビュー | 文書ごとに書いた直後 | 変更の重さで 3 段階から選ぶ（§4） |

順序（Spec → テスト → 実装）は新規作成と同じである。

## 2. 入口は 2 つ

| 入口 | 起点 | 最初に決めること |
| --- | --- | --- |
| 要件が変わった | 要件（`REQUIREMENTS.md`）の変更 | 変更の種類（§3） |
| 実装中に設計の欠陥が見つかった | 設計書・テスト設計・実装のどこかで見つかった矛盾や欠落 | 欠陥がどの文書に属するか |

実装中に見つかった欠陥は、見つかった場所ではなく、**その事実を持つべき文書**に属する。

- 要件の記述そのものが誤っている → 要件が変わる入口に合流する。
- 要件は正しく、設計書やテスト設計がそれを正しく表していない → その文書から下を直す。要件は変えない。
- 文書はすべて正しく、実装だけが違う → 文書は変えない。欠陥を捕まえるテストを足して Red を確かめてから実装を直す。

どの文書に属するか決められないときは、ユーザーに確かめる。実装に合わせて文書を書き換えると、Spec を正本にする意味が失われる。

## 3. 直す文書を依存関係から決める

文書の間には「上の文書の決定が変わると、下の文書が動きうる」という依存関係がある。依存関係は
`docs.lineup`（[`spec-lineup.md`](spec-lineup.md)）で決まり、実際のファイルは `docs.layout` で決まる。

- `single`: 要件 → `TECH_DESIGN.md` → `TEST_PLAN.md` → テスト → 実装
- `layered`: 要件 → `API_DESIGN.md` → `SCREEN_DESIGN.md`（API が返すコードを画面が受ける）→ 層別のテスト設計 → `TEST_DESIGN.md` → テスト → 実装
- common 階層（`TABLE_DEFINITION.md`・`API_SPEC.md`・`DESIGN.md` など）は、feature の設計書の上に入る。要件の変更がテーブルや API の形に及ぶときは、common も直す対象になる。

`revising-specs` の `scripts/spec-propagation.sh targets` が、変更が属する文書から依存の向きにたどれる文書を、設定から引いて直す順に出す。
出てきた文書は 1 件ずつ「直す」か「変わらない」かを決め、変わらないと決めた文書には根拠を残す。
変更の種類ごとに、どの文書が動くことが多いかの目安は skill の `references/change-kinds.md` にある。

依存関係は ID の参照しか表さないので、説明文が暗に頼っている事実は拾えない。依存関係から出た候補に、§5 の検索の結果を重ねて決める。

## 4. レビューの強さ

変更の重さに合わせて、レビューの形を 3 段階から選ぶ。

| 段階 | 形 | 当てはまる変更 |
| --- | --- | --- |
| 自動検査だけ | reviewer を起動しない。検査（`trace-audit.sh`・§5 の残りの確認・§6 の転記の検査）とテストだけで通す | **意味を変えない追随**に限る。文言・体裁の修正、ID の参照の差し替え、上の文書の変更に合わせた要約の書き換え |
| まとめて 1 回 | 直す文書をすべて書き終えてから、触った文書の reviewer を 1 回ずつ並列に起動する | 意味が変わる設計書・テスト設計の変更（既定） |
| 文書ごと | 書いた直後に、その文書の reviewer を起動する。指摘を直してから下の文書に進む | 要件の意味が変わる変更と、破壊的な変更（テーブルの列・型・制約の変更、API の互換を壊す変更、レスポンスコードの意味の変更） |

- 判断の基準は行数ではなく、**意味が変わるかどうか**である。1 行でも意味が変わる変更は、自動検査だけで通さない。
  検査は形を確かめるだけで、意味の変化は読まないと分からない。
- 要件と破壊的な変更を文書ごとにするのは、そこでの誤りを最後に見つけると、下の文書をすべて書き直すことになるためである。
  下の文書どうしは互いに独立しているので、まとめて 1 回で足りる。
- 破壊的な変更は、着手の前に影響範囲を添えてユーザーの承認を取る。改修の対象には、すでに動いている実装とデータがある。
- どの段階にしたかは、メインのセッションが差分を見て決め、判断と根拠を報告に書く。書けないなら軽い段階を選ばない。
- reviewer の割り当ては新規作成と同じである（要件は `requirements-reviewer`、設計書とテスト設計は組ごとに `tech-specs-reviewer`、テストは `test-reviewer`）。

## 5. 変更の伝播

上の文書の決定が変わったら、影響を受ける文書を次の手順で洗い出し、漏れなく直す。

1. **ID と変更前の語の両方で検索する。** 変わった決定の ID だけでなく、変更前の説明文に使っていた語でも探す。
   意味が反対になるような変更では、ID はそのまま残り、壊れるのは説明文のほうである。ID だけで探すと、古い説明文が残る。
2. **同じ修正の文を、直す文書すべてに当てる。** 変わった決定を 1 つの文にまとめ、それぞれの文書に同じ文で反映する。
   文書ごとに言い換えると、同じ決定が文書ごとに違う意味で読まれる。複数の担当（並行するセッションや subagent）に分けて直すときは、
   同じ文を同時にすべての担当に渡す。
3. **直し終えたら、1 と同じ検索で古い記述が残っていないことを確かめる。**
   `spec-propagation.sh search --expect-none` に 1 と同じ語を渡し、0 件になることを確かめる。

ID の参照の抜けは `trace-audit.sh` が確かめる。説明文の語の残りは、この手順の検索で確かめる。

## 6. 転記せず参照する

件数・一覧・しきい値のように、ほかの文書でも使う値は、**正本の文書だけが持つ**。ほかの文書は ID やリンクで正本を参照し、値を書き写さない。
書き写した値は、正本が変わったときに気づかれないまま古くなる。

- **件数・一覧・しきい値は正本だけに書く。** 例: 上限値は非機能要件の表だけが持ち、設計書は表の行を参照する。
  レスポンスコードの一覧は `API_DESIGN.md` だけが持ち、画面設計はコードを ID で受ける。
- **ほかの文書の作成状況や件数を、本文に断定の形で書かない。** 「この機能の画面は N 画面で、うち M 画面は未作成」のような文は、
  ほかの文書が変わるたびに偽になる。いまの状況が必要なら、検査やコマンドで調べる形にする。
- **設計書だけでなく、規約・skill・agent の定義にも同じ規律を適用する。** skill がほかの skill の手順を書き写すと、
  正本の手順が変わったときに食い違う。手順はその skill を参照する（[`../../../docs/config-driven-authoring.md`](../../../docs/config-driven-authoring.md) §8）。

`documenting-requirements` の `scripts/state-claims.sh` が、1 つの文の中に件数の句（「N 画面」のような数字と成果物の名詞）と状態の語（「未作成」）が
両方ある形を見つける。片方だけの文は見ない（「行が 0 件のとき」のようなデータの状態の記述を誤って拾うため）。
語彙は `.stdd.config.yml` の `docs.state_claims` で変えられる。この検査が見つけるのは転記の一部だけなので、残りはレビューで読む。

## 7. 規律と自動化の対応

| 規律 | 確かめる手段 | 自動化しない部分と理由 |
| --- | --- | --- |
| 改修で直す文書を、人が列挙せず依存関係から決める | `spec-propagation.sh targets`（`docs.lineup` と `docs.layout` から引く） | 候補のうちどれを直すかは、変更の意味を読んで決める。決めた根拠を報告に残す |
| 自動検査だけで通すのは意味を変えない追随に限る | skill の手順（判断と根拠を報告に書く） | 意味が変わるかどうかは読まないと判断できない |
| ID と変更前の語で検索し、直し終えたら古い記述の残りが無いことを確かめる | `spec-propagation.sh search --expect-none`。ID の参照は `trace-audit.sh` | どの語で探すかは変更の内容から決める |
| 同じ修正の文をすべての文書に当てる | skill の手順 | 文の同一性は文書の文脈に合わせた書き方と両立させる必要があり、機械で強制しない |
| ほかの文書の作成状況や件数を断定しない | `state-claims.sh`（件数の句と状態の語が同じ文にある形）。STDD の skill・agent・規約の定義は `test/state-claims.test.sh` が確かめる | 共起しない形（件数だけ、状況だけ）は誤検出が多いので見ない。レビューで読む |
| 件数・一覧・しきい値は正本だけが持つ | レビュー | どれが正本かは文書の分担（[`spec-lineup.md`](spec-lineup.md) §3）で決まり、値の同一性を機械で突き合わせる検査はまだ無い |

## 8. 対象にしないもの

- 未決事項（確認待ちの論点）の管理と、それが残っているときに実装を始めない条件。プロジェクトによって運用が違うので、STDD では定めない。
  確認が必要な点の書き方は `documenting-requirements` の要確認マーカーを使う。
- テンプレートの版が上がったときに、作成済みの文書を新しい版に合わせる手順（版の宣言は [`spec-lineup.md`](spec-lineup.md) §7）。
