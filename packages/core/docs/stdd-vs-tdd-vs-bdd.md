# STDD vs TDD vs BDD — 比較と使い分け

本ドキュメントは STDD (Spec and Test Driven Development) を、隣接する 2 つの開発手法 — TDD (Test-Driven Development) と BDD (Behavior-Driven Development) — と比較し、それぞれの強みと典型ユースケースを整理する。

## 1. 1 行サマリー

| 手法 | コアアイデア                                              | 主役のアーティファクト                |
| ---- | --------------------------------------------------------- | ------------------------------------- |
| TDD  | テストを先に書き、それを通す最小実装を作る                | テストコード                          |
| BDD  | 振る舞いを自然言語に近い DSL (Given-When-Then) で記述する | フィーチャーファイル (例: .feature)   |
| STDD | 仕様 (REQUIREMENTS + TECH_DESIGN) を先に書き、それを SSoT とする | Spec ドキュメント (Markdown) |

---

## 2. 詳細比較

| 観点                                  | TDD                                | BDD                                              | STDD                                                  |
| ------------------------------------- | ---------------------------------- | ------------------------------------------------ | ----------------------------------------------------- |
| **第一に書くもの**                    | 単体テスト                         | フィーチャーファイル (Gherkin 等)                | REQUIREMENTS.md + TECH_DESIGN.md                      |
| **誰が書く?**                         | エンジニア                         | エンジニア + ステークホルダーで合意              | エンジニア + ステークホルダーで合意                   |
| **誰が読める?**                       | エンジニアのみ                     | エンジニア + ステークホルダー (Gherkin は読める) | エンジニア + ステークホルダー (Markdown は読める)     |
| **粒度**                              | 関数 / メソッド                    | ユースケース (ユーザー操作の単位)                | 機能 (feature)                                        |
| **対象テストレベル**                  | Unit が中心                        | E2E / Acceptance が中心                          | Unit / Integration / E2E を Test Strategy で割り当てる |
| **Priority / 重要度のマーキング**     | なし                               | タグ機能はあるが運用は任意                       | 必須 (P0 / P1 / P2)                                   |
| **AI エージェントとの相性**           | ◯ (テストを与えれば実装は生成可能) | △ (DSL のパース / 拡張が必要)                    | ◎ (Markdown と Test Strategy をそのまま読める)         |
| **ステークホルダーとの合意形成**      | △ (テストを直接見せにくい)         | ◯ (フィーチャーは読める)                         | ◎ (User Journey と UI を含めて議論できる)              |
| **進捗ステータスの所在**              | コミット履歴 / イシュートラッカー  | 同上                                             | PLAN ドキュメント (Spec は常に最新仕様のみ)            |
| **デザインドキュメントとの分離**      | なし (テストに混在しがち)          | フィーチャーの外で別管理                         | TECH_DESIGN.md で明確に分離                            |
| **ツール依存**                        | 弱 (任意のテストフレームワークで可)  | 強 (Cucumber / Behave 等の専用ツールが必要)      | 弱 (Markdown + 任意のテストフレームワーク)             |

---

## 3. STDD を選ぶ判断基準

以下の条件のうち、**2 つ以上当てはまる場合は STDD が有利**:

1. **AI エージェントと共同開発する** (Claude Code / Cursor / Copilot Workspaces 等)
   → AI は Spec を自然言語で読み取り、Test Strategy に従ってテスト → 実装まで自律的に進められる

2. **ステークホルダーと仕様レビューを密に回したい**
   → REQUIREMENTS.md は User Journey と UI を含む Markdown なので、PM / デザイナーが直接コメントできる

3. **エラーケースとエッジケースを暗黙仕様化したくない**
   → STDD はエラーも正規の Journey として記述させ、Priority を付けることで「明示的に扱う」ことを強制する

4. **テスト戦略 (E2E をどこまで書くか) を継続的に意思決定したい**
   → TECH_DESIGN.md の Test Strategy 表が「なぜこの Journey は E2E で守るのか / 守らないのか」の合意の場になる

5. **複数アプリ / 複数チームで開発する**
   → `.stdd.config.yml` の `apps[]` と `docs.layout` で、機能ごとに対応する Spec パスを機械的に決定できる

---

## 4. STDD を選ばない方がよいケース

逆に、以下のケースでは STDD の重さがメリットを上回る可能性がある:

- **小規模なライブラリ / CLI**: ユーザー Journey が単純で、README + テストで十分
- **試行錯誤フェーズ (探索的プロトタイピング)**: 仕様自体が定まっていないので、TDD で実験 → 後から Spec 化する方が早い
- **ステークホルダーが 1 人 (= 自分自身)**: 合意形成のコストがそもそも発生しない
- **既存コードベースで Spec を遡及作成する余力がない**: 部分的に reverse-engineering を進めるのが先

## 5. 3 手法の使い分け早見表

| シチュエーション                                          | おすすめ                      |
| --------------------------------------------------------- | ----------------------------- |
| 個人開発 / OSS ライブラリ                                 | TDD                           |
| ステークホルダーがいる業務アプリ / Web サービス           | **STDD**                      |
| 受け入れテスト駆動でリリース判定したい (規制業界等)        | BDD                           |
| AI エージェントに包括的に実装を任せたい                   | **STDD**                      |
| 仕様変更が頻繁で「何を作っているか」を毎週共有したい      | **STDD** (Spec が SSoT として機能) |
| 1 機能の細部 (バリデーション、計算ロジック) を磨きたい    | TDD (STDD と併用可)           |
| ステークホルダーがテストファイル自体を読む文化            | BDD                           |

---

## 6. 併用パターン

STDD は TDD / BDD を排除するものではない。

- **STDD + TDD**: 一般的。Spec で What を固定し、TDD で How を細かく回す。本ガイドのデフォルト姿勢
- **STDD + BDD**: 受け入れテストを Gherkin で記述する場合、REQUIREMENTS.md の User Journey から `.feature` を生成すると相性が良い
- **STDD のみ (テスト記述なし)**: NG。Spec だけ書いてテストを書かないと STDD ではなく、ただのドキュメント駆動になる

---

## 7. 参考: 各手法の歴史的経緯

- TDD: Kent Beck らによる Extreme Programming (1999) で体系化。Unit テスト中心
- BDD: Dan North が 2006 年に提唱。TDD の「テスト」を「振る舞い (Behavior)」に置き換えることで会話可能にした
- STDD: AI コーディングエージェントの普及 (2023 - 2026) に呼応して、Spec を SSoT とする運用が各所で自然発生的に成立。本リポジトリの STDD はその一実装である
