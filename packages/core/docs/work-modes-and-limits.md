# 作業モードと適用限界

STDD 方法論（[`stdd-methodology.md`](stdd-methodology.md)）の一章。STDD をどの局面で、どこまで厳密に適用するかを定める。
前半は作業の進め方を一時的に軽くする**緊急モード**と、その間に生じた負債の扱い、後半は STDD が向かない局面と、
その判断の目安を書く。

## 1. 目的

STDD は、既定では品質を最優先にした進め方になっている。Spec を先に書き、専門エージェントに分業させ、レビューと
品質ゲートを通してからマージする。この進め方は、要件の抜け漏れや重大な不具合を防ぐ一方で、時間がかかる。
障害対応や期限の迫った修正のように、速さを優先すべき場面では、この重さがそのままボトルネックになる。

そこで、次の 2 つを方法論として明示する。

- **緩めてよいものと、緩めてはいけないものの線引き。** 速さが必要なときに、何を省いてよく、何は省いてはいけないか。
- **適用を見送る・緩める判断の目安。** そもそも STDD をそのまま当てるべきでない局面はどこか。

## 2. 作業モード

作業モードは**通常**と**緊急**の 2 つで、ブランチごとに決まる。既定は通常モードで、`AGENTS.md` と規約・skill の工程を
そのまま通す。

なお、`auto-implement` の「実行モード」（`full` / `spec-only` / `impl-only` / `quick`）は、どのフェーズを実行するかを
課題の種類で選ぶもので、作業モードとは別の軸である。緊急モードは、どの実行モードとも組み合わせられる。

### 2.1 緊急モード

緊急モードは、**ユーザーが着手時に明示した場合に限って**入る。緊急モードのブランチでは、次のものを必須にしない。

- **分業。** 専門エージェント（writer / reviewer / implementer など）を使うかどうかは、メインのエージェントが判断する。
- **レビューの回数。** エージェントによるレビューは省いてよく、行う場合も 1 回で打ち切ってよい。
- **品質ゲートの合格。** テスト・ビルド・トレーサビリティ監査が不合格のままでも、push と PR の作成を止めない。

一方で、次のものは緊急モードでも守る。

- **Spec → テスト → 実装の順序。** 振る舞いを変えるなら先に Spec を直し、実装と同じ PR に入れる。テストの無い実装だけを
  入れることはしない（テストが先に失敗すること＝ Red の確認は省いてよい）。
- **PR 本文への明記。** 緊急モードで作ったこと、省いた工程、不合格のまま残した検査、後追いが要るものを書く。
- **負債の記録。** 緩めた分を、機能ごとの負債として記録する（→ 2.3）。

具体的にどの工程を必須にしないかの一覧は、skill `choosing-work-mode` の §3 にある。一覧はオリジナルに現在ある工程に
合わせて書いており、レビュー工程を変えたときは、その一覧だけを差し替える。

| 仕組み | 担当 | 置き場 |
| --- | --- | --- |
| 作業モードの選択・宣言・解除 | `choosing-work-mode` skill（`scripts/work-mode.sh`） | git の共通ディレクトリ配下の `stdd-work-mode/`（作業ツリーの外） |
| ユーザーの申し出の記録 | フック `work-mode-prompt.sh`（UserPromptSubmit） | 同上 |
| 品質ゲートの緩和 | フック `pre-push-check.sh` | — |
| PR 本文と工程テレメトリの確認 | `create-pr` skill（`scripts/pr-telemetry.sh`。区分 `emergency`） | PR コメント |
| 負債の記録と解消 | `settling-emergency-debt` skill（`scripts/emergency-debt.sh`） | GitHub issue（`emergency_mode.debt_label` ラベル） |

### 2.2 AI が自分で切り替えない仕組み

緊急モードは工程を軽くするので、エージェントにとっては「楽な道」になる。エージェントが「時間が無さそうだから」と
自分の判断で入ると、レビューと品質ゲートが黙って外れる。そのため、入る条件はユーザーの明示だけに限り、次のように
仕組みの側でも支える。

1. ユーザーの発言に「緊急モード」が含まれると、UserPromptSubmit のフックが**申し出**として記録する。
   このフックはユーザーの発言でしか動かないので、エージェントの出力やツールの結果からは記録されない。
2. `work-mode.sh declare` は、有効期限内（既定 120 分）の申し出の記録が無いと宣言しない。1 回の申し出で宣言できるのは
   1 回だけで、主ブランチでは宣言できない。
3. 「急ぎで」のような速度の表現だけのときは、skill が作業モードを 1 問だけ尋ねる。答えを待たずに宣言しない。
4. 宣言はブランチに閉じる。新しいブランチは必ず通常モードから始まる。

置き場は誰でも書けるので、この仕組みは改ざんを防ぐものではない。記録は「ユーザーが選んだことの控え」であり、
申し出や宣言のファイルを直接書かないことは、skill と規約で禁じている。

### 2.3 負債の記録と解消

緊急モードで緩めた分は、そのままにすると Spec と実装の食い違いとして残り、次にその機能を改修する人がつまずく。
そこで、緩めた分を**機能ごとの負債**として GitHub issue に記録し、あとで解消する。

- **記録**: 緊急モードの PR を作ったら、触れた機能ごとに負債 issue へ積む（`emergency-debt.sh record`）。
  機能ごとに open な issue は 1 つで、PR を作るたびに追記していく。
- **解消**: 由来の PR を事後レビューにかけ、Spec と実装の食い違いを仕分ける。実装の振る舞いが妥当なら Spec を実装に
  合わせ、実装が誤りなら実装を直す。認可や入力検証のように安全に関わる振る舞いと、どちらが正しいか決められないものは、
  人の判断に回す。最後に通常モードのレビューと品質ゲートを通して PR にする（`settling-emergency-debt`）。
- **閉じる**: 解消の PR がマージされたら issue を閉じる。解消に着手したあとで積まれた負債が残っていれば閉じない
  （`emergency-debt.sh close` が確かめる）。

緊急モードの PR は工程テレメトリで区分 `emergency` として記録され、`measuring-dev-process` の集計ではレビュー回数の
統計から外して数える。緊急モードの割合が高い状態が続くなら、通常の進め方が重すぎる兆候として扱う（→ 3.2）。

## 3. 適用限界

### 3.1 STDD が向かない局面

STDD は既定で品質を優先しており、そのぶん開発の速度は落ちる。品質と速度はトレードオフであり、局面によっては
STDD 自体がボトルネックになる。

- **要件が頻繁に変わる、または固まっていない段階。** Spec を書いても、すぐに書き直すことになる。整合性を保つための
  時間が、作る時間を上回りやすい。
- **速度が求められる段階。** 動くものを先に作り、あとからリバースエンジニアリングで文書を起こすほうが速く、効率的な
  場合がある。ドキュメントと実装の食い違いを、期間を区切って意図的に許すという選択肢もある。緊急モードはその一つの形である。
- **ゼロから作る段階で厳密に適用しすぎる場合。** 整合性の確保に時間を取られ、あとで不要とわかる受入基準が増える。
  共通設計の中には、実装を先に進めた結果として見えてくるものもある。プロジェクトに合った文書の構成と章立てを決めるにも
  時間がかかり、設計を進めるうちにテンプレートを直し、それを既存の文書に当て直す手間も生じる。
- **期限があり、ハーネスに慣れていない開発者が中心になる場合。** skill・agent・フック・規約の一式は、作った人以外には
  中身が見えにくい。使い方を説明する時間が取れないまま厳密に適用すると、負担が大きくなる。

逆に、要件を網羅して抜け漏れなく実装したい場合や、重大な不具合を防ぎながら進めたい場合は、STDD の効果が出やすい。

### 3.2 判断の目安

| 局面 | 目安 |
| --- | --- |
| 要件が固まっており、要件の網羅と品質を優先できる | 通常モードで適用する |
| 障害対応・期限の迫った修正など、一時的に速さが必要 | ユーザーが明示して緊急モードを使い、負債を記録してあとで解消する |
| 要件が頻繁に変わる・試作の段階 | 試作は STDD の外で進め、要件が固まった時点で `reverse-engineering-feature-spec` で Spec とテストを起こし、以降は通常モードで運用する |
| ゼロから作る段階 | 最初から全機能を厳密に進めず、common 階層と代表的な機能で文書の構成を決めてから広げる（`starting-new-with-stdd`・`tailoring-spec-format`）。文書のたたき台を作り、運用しながら直す前提で進める |
| チームで使い始める・ハーネスに慣れていない開発者が多い | 先に使い方と判断が要る箇所の決め方を説明し、判断を表や既定値で決めておく（導入ガイドの「チームに導入する場合の注意」） |
| 緊急モードの割合が高い状態が続く | 通常の進め方が重すぎる兆候とみなし、`measuring-dev-process` で時間のかかっている工程を特定して見直す |
