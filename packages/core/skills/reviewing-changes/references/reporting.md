# レビューの報告の書式

STDD のすべてのレビュー（PR 前レビュー、auto-implement の Phase 1a・1b・2.5）で、reviewer が使う報告の書式。
呼び出し元は依頼文でこのファイルのパスを渡す。

## 1. 指摘ごとに書くもの

指摘には重大度（Critical / Major / Minor、High / Medium / Low）も総合判定（PASS など）も付けない。次の 4 項目と確信の段階を書き、
処置（直すかどうか）は書かない。処置と、次へ進むかどうかは、呼び出し元が 4 項目からスクリプトで決める。

| 項目 | 書くこと |
| --- | --- |
| 発生条件 | どの入力・状態・権限で起きるか（Spec の指摘では、どの記述をどう読むと誤るか）。根拠と同じく現物から引く |
| 頻度 | `常時`・`条件付き`・`稀`（§2・§3 の目安） |
| 影響 | `致命`・`支障`・`軽微`（§2・§3 の目安） |
| 影響先 | ユースケースの ID、画面、API の操作、権限の範囲、ファイルのパス、章、skill・agent の名前。**実在する ID とパスだけ**を、複数あれば読点で区切って並べる |
| 確信の段階 | どこまで確かめたか（`assessing-change-impact` §1 の 1〜5）。根拠の `ファイル:行` を添える |

- 影響は、頻度とは独立に、起きたときの重さで付ける。判定の問いは「起きたとき、誰かが気づけるか・戻せるか・誰かの判断を誤らせるか」。
- 4 項目は起きたらどれくらい困るか、確信の段階はどこまで確かめたかで、別の物差しである。両方を書く。
- 迷ったら重いほうを選ぶ。呼び出し元は 4 項目を上げることはできるが、下げることはできない。
- **セキュリティの観点**では頻度を書かない。攻撃する側は稀な条件を自分で作れるためである。影響は、攻撃が成功したときの結果で判定する。

## 2. 実装・テスト・ハーネスの指摘の目安

| 影響 | 判定の問い | 実装の指摘 | ハーネス・規約の指摘 |
| --- | --- | --- | --- |
| `致命` | 気づけない、または戻せない。誤ったものが作られ続ける | データの破損・消失、認可の回避、利用者の範囲を越えたアクセス、金額の誤り、監査の記録の欠落 | 検査が失敗を見逃す経路、検査を黙らせられる経路 |
| `支障` | 気づけて戻せるが、作業が止まるか誤った結果が出る | 誤った表示・状態・応答、回復できるエラー | 誤検知や誤った案内で手戻りが 1 回増える |
| `軽微` | 作業や利用に影響しない | 見た目・文言・ログの質 | 文書の整形・リンク・読みにくさ |

**テストの指摘の影響は、そのテストが見逃す欠陥の影響を引き継ぐ。** テストそのものの出来では付けない。

| 頻度 | 判定の問い | 実装の指摘 | ハーネスの指摘 |
| --- | --- | --- | --- |
| `常時` | 普通に使えば当たる | 通常の操作で必ず起きる | どの PR でも通る経路 |
| `条件付き` | 決まった条件で当たる | 特定の入力・状態・権限で起きる | 特定の担当・契機でだけ通る |
| `稀` | 条件が重ならないと当たらない | 複数の条件の重なり、競合、外部の障害の組み合わせでだけ起きる | 打ち切り・やり直しなどの例外の経路でだけ通る |

## 3. Spec の指摘の目安

要件・技術設計・テスト設計の指摘は、実行で確かめられないので、同じ 4 項目を Spec 用の目安で付ける。
影響は「この記述のまま作ったら何が起きるか」、頻度は「この記述を読んで実装する人が毎回引っかかるか」で決める。

| 影響 | 判定の問い | 例 |
| --- | --- | --- |
| `致命` | この記述のまま作ると、誤ったものが作られ、作った後も誤りに気づけない | 誤った受入基準・業務ルール、権限やデータの範囲の誤り、要件と設計の矛盾で片方が誤っている、P0 のユースケースのテスト設計の欠落 |
| `支障` | 読み手が迷うか手戻りが出るが、正本をたどれば正しく作れる | 曖昧な語（「適切に」など）、ユースケースとテスト設計の対応づけの漏れ、経緯や履歴の混入（SSOT 原則の違反）、例外・境界の書き漏れ |
| `軽微` | 作るものに影響しない | 機械的に導ける情報のずれ、表現の重複・言い回し、書式 |

| 頻度 | 判定の問い | 例 |
| --- | --- | --- |
| `常時` | この記述を読んで実装する人が毎回引っかかる | 主要なユースケースの振る舞い、必ず読まれる章（概要・データの形・API の契約） |
| `条件付き` | 特定の機能・改修・入力を扱うときだけ引っかかる | 特定の画面や API の項目、特定のエラーケース |
| `稀` | 読まれる工程がほとんど想定されない | 補足、例外の経路の説明、参考情報 |

## 4. テストとコードの担当（`test-reviewer`・`code-reviewer`）の追加の決まり

- **処置が「直す」に当たりうる指摘は、実行して確かめる（確信の段階 4 以上）。** 次の 3 つを付ける。
  - **再現の手順**: そのまま実行できるコマンド（一時的に置いたテストやスクリプトがあれば、その全文も）
  - **意図した出力**: 正しく実装されていれば出るはずの結果
  - **実際の出力**: 実行して得た結果（実行できなかったときは、予想される結果とその理由）
- **実行する場所**: 自分の作業ツリー（`isolation: worktree`）で、依頼のコミットに `git checkout --detach <SHA>` で切り替えてから実行する。
  呼び出し元は、その手順をもう一度実行して確かめる。作業ツリーを分けられないとき（Codex、作業ツリーを分けずに動く
  agent teams のメンバー）は、シェルを読み取りにだけ使い、手順を書いて実行は呼び出し元に任せる。呼び出し元は、
  レビューするコミットから作った使い捨ての作業ツリーで実行する。
- **実行で確かめられなかった「直す」の指摘は「未確認」になる。** 終わりの条件に数えられず、別に並べられる。
  確かめられないと分かっていても、指摘として出してよい。
- 次のものは指摘に含めない。必要なら「気づき」に 1 行で書く。
  - 書き方・命名・構造の好み
  - 将来の変更で初めて問題になるリスク（いまのコードとテストでは失敗を示せないもの）
- 要件や設計との食い違いを見つけたときは、§3 の目安で書き、再現の手順の代わりに食い違う Spec の箇所を `ファイル:行` で示す。

## 5. 報告の形

```markdown
## 指摘

### <ID>: <一行の要約>
- 発生条件: ...
- 頻度: 常時 | 条件付き | 稀（セキュリティの観点では書かない）
- 影響: 致命 | 支障 | 軽微 — <判定の理由>
- 影響先: ...
- 確信の段階: 1〜5（根拠: `ファイル:行`）
- 再現の手順・意図した出力・実際の出力（テストとコードの担当の「直す」に当たりうる指摘）
- 直し方の案: ...

## 確かめて問題が無かったもの
- <対象>: <理由>

## 気づき
- <プロセス上の課題、指摘に含めなかったもの。無ければ「なし」>

指摘 ID: <ID>, <ID>
```

- ID は `R<ラウンド>-<担当>-<連番>`（例: `R2-security-1`）。担当とラウンドは依頼文に書かれている。
  ラウンドの無いレビュー（Phase 1a・1b・2.5）は `<Phase>-<担当>-<連番>`（例: `1a-requirements-1`）。
- **最後の行は必ず `指摘 ID:` の一覧にする。** 指摘が無ければ `指摘 ID: なし`。呼び出し元はこの行を読んで、
  指摘が記録から漏れていないかを確かめる。
