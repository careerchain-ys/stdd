# 変更の種類と、動くことが多い文書

`revising-specs` の §3 で使う目安。直す文書の候補は `spec-propagation.sh targets` が依存関係から出す。
この表は、候補のうちどれが動くことが多いかと、レビューの強さの目安を示す。表に当てはまらない変更でも、候補を 1 件ずつ確かめる手順は変わらない。

文書の分担・行の ID はテンプレート（`documenting-tech-specs` の `templates/`）と `references/doc-structure.json` が正本である。

## 1. 要件が起点の変更

| 変更の種類 | `single` で動くことが多い文書 | `layered` で動くことが多い文書 | レビューの強さの目安 |
| --- | --- | --- | --- |
| 文言・体裁（意味を変えない） | 要件だけ | 要件だけ | 自動検査だけ |
| 受入基準の意味の変更 | `TECH_DESIGN.md` の該当箇所、`TEST_PLAN.md` の担保 | 検索で当たった側の設計書（`API_DESIGN.md` / `SCREEN_DESIGN.md`）、層別のテスト設計、`TEST_DESIGN.md` の担保の行 | 要件は文書ごと、下はまとめて 1 回 |
| 受入基準の追加 | 同上に加えて `TEST_PLAN.md` の行を足す | 同上に加えて `TEST_DESIGN.md` の行を足し、担保する層を決める | 要件は文書ごと、下はまとめて 1 回 |
| ユースケースの振る舞いの変更（手順・主体・Priority） | `TECH_DESIGN.md`、`TEST_PLAN.md`（Priority が変わるとテストレベルが変わる） | 検索で当たった側の設計書、`TEST_DESIGN.md` の E2E のシナリオ手順と担保のレベル | 要件は文書ごと、下はまとめて 1 回 |
| ユースケースの追加 | すべての文書 | 層は内容で決める。画面を持たないユースケースなら画面の 2 本を作らない。API の操作が増えるなら common の `API_SPEC.md` も | 要件は文書ごと、下はまとめて 1 回 |
| 受入基準・ユースケースの削除 | ID を参照している箇所の除去 | ID を参照している箇所の除去（設計書の対応ユースケース、テスト設計の担保の行） | 要件は文書ごと。参照の除去だけなら下は自動検査だけ |
| 業務ルール（`BR`）の追加・変更 | `TECH_DESIGN.md` のロジック設計 | `API_DESIGN.md` の業務ルールの実現方法と `API_TEST_DESIGN.md`。画面でも同じ判定をするなら `SCREEN_DESIGN.md` のバリデーション | 要件は文書ごと、下はまとめて 1 回 |

- 削除した ID は欠番にし、番号を詰めない。詰めると既存の参照とテストの名前が別の要求を指す。
- 削除する ID をほかの受入基準や業務ルールが前提にしていないかを、`spec-propagation.sh search` で確かめてから消す。
- 受入基準を削除しても実装やテストに ID が残っていることがある。`--also` でテストと実装のディレクトリも探す。

## 2. 技術 spec が起点の変更

| 変更の種類 | 起点 | 動くことが多い文書 | レビューの強さの目安 |
| --- | --- | --- | --- |
| レスポンスコードの追加（`layered`） | `API_DESIGN.md` | 発生条件 → その操作を呼ぶ**すべての** `SCREEN_DESIGN.md` のレスポンス処理 → 層別のテスト設計 | まとめて 1 回 |
| レスポンスコードの意味の変更（`layered`） | `API_DESIGN.md` | 既定は、新しいコードを足して古いコードを使わなくする（呼び出し側の追随が要らない）。意味そのものを変えるなら破壊的な変更として扱い、呼ぶ画面をすべて直す | 文書ごと（意味を変えるとき） |
| レスポンスコードの削除（`layered`） | `API_DESIGN.md` | 画面とテスト設計からの参照を除き、参照が 0 件になってから削除する。番号は再利用しない | まとめて 1 回 |
| 画面の表示・文言・項目・遷移だけ | `SCREEN_DESIGN.md`（`single` は `TECH_DESIGN.md` の画面項目） | `SCREEN_TEST_DESIGN.md`（`single` は `TEST_PLAN.md`）。API とテーブルは動かない | まとめて 1 回 |
| テーブル・API の形の変更 | common の `TABLE_DEFINITION.md` / `API_SPEC.md` | その形を使う設計書（`single` は `TECH_DESIGN.md`、`layered` は `API_DESIGN.md` と、API の形を受ける `SCREEN_DESIGN.md`） | 互換を壊すなら文書ごと（着手前にユーザーの承認） |
| common の横断ルールの変更（common の要件・`ARCHITECTURE.md`・`DESIGN.md`） | common の文書 | そのルールに触れているすべての機能の文書。ID で探し、ID を持たない規律は対象の語で探し、層に閉じる規律はその層の文書を順に見る | まとめて 1 回 |

- 横断ルールの変更で、同じ作業で直しきれない機能の文書は、`recording-dev-feedback` の控えに残して後で起票する。
- 認可・可視性に触れる変更は、API と画面の両方の設計書を候補にし、同じ規則を述べているすべての文書を reviewer にまとめて渡す。
  片方の層だけを渡すと、層の間の食い違いが見つからない。
